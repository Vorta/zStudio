# Source projects

Opening a source project shows a centered map picker. Each existing `data/mN` folder with a matching `gamegen/mN.gs` entry script gets a button, sorted by mission number. A missing model or broken script does not hide its map; opening it reports the build problem. The picker has no Diagnostics pane: a map that could not open says why on the picker, and a check, export or initialization run from it lists its failures and notes in its result window (Diagnostics shows them once a map is open). **New** is disabled. Selecting a map replaces the picker with centered **Loading...** text until its preview is ready; cancellation or a failed opening restores the picker. Source projects use this map workspace instead of the Files, Assets and Search browser; the GUI opens only source projects, and compiled game folders open only through MCP `zstudio_open_root` (without `project`).

The map picker lists the single-player maps (m1–m6) and the multiplayer maps as separate groups, six to a row. One map is open at a time. The back arrow left of the **Whole world** heading returns to the map picker through Save/Discard/Cancel, retaining the map on Cancel. The map uses the mission-start preview and difficulty preference. Its World outliner (left; see [the source map editor](scene-inspection.md#source-map-editor)) starts at `world` and follows the authored glTF hierarchy, including groups removed during compilation. The world tree holds what the map itself holds; objects the mission adds in later passes follow as top-level trees of their own: **aiv**, the units the mission's AIV resources place, and **puppies**, the pickups its puppies resources place (both list every difficulty's entries tagged with the difficulties that place them, such as `E/M/H`, with the other difficulties' rows dimmed), and **anim**, the objects the startup animations place (or hide until an animation places them). Objects a mission animation binds to by name are marked with an icon after their name, whose tooltip names the animations. For example, m1 retains `world → group42 → group43 → tur_101`. Node-type icons distinguish source groups and referenced objects; each referenced glTF occurrence and placed mission actor remains one selectable object. Clicking a mesh inside a turret selects that turret while retaining the exact hit polygon for surface inspection. Groups removed by the game build remain inspectable with their source file and glTF node index. They have no compiled node slot or unsupported placement editing actions. Primary parent details follow the selected authored object; clicked internal meshes expose their own surface parent details separately.

`zstudio_source_map_parts` and `zstudio_source_map_parts_visibility` (MCP only; the tree has no Parts button) change only a selected reference instance's editor visibility, and reset restores the mission-start defaults. Hidden parents, LOD and unplaced-actor suppression still apply. Overrides survive preview refreshes and cache rebuilds while their authoritative source dependencies remain unchanged. Changing a model, its reference/load chain or an actor resource resets affected overrides rather than risk applying them to a different part; even a transform-only source edit can cause that reset. Closing the map clears all overrides. These overrides do not modify glTF flags, dirty the project or add undo steps. A source map has no editing lock: click an object and edit it in its card. Explicit source Properties edits retain their existing behavior. Placement edits target the map/script or the actor's resource record. Startup-animation-controlled positions remain inspectable but cannot be moved through the map workspace.

Source-world opening and rebuilding prepare the decoded world, slot map and provenance off the UI thread, with cancellation and revision checks before publication. Object inspection reuses that prepared model. Structural edits use one bounded provenance index per plan when preserving instance zones. Terrain reference discovery validates auxiliary glTF structure before inspecting its nodes and bounds aggregate reference work; malformed structure or exhausted capacity refuses the operation rather than publishing an incomplete reference set. Save cancellation also reaches recovery-journal cleanup before a new publication starts; cleanup after a committed save remains independent of request cancellation.

RECOIL's shipped ZBD files are build outputs. The studio originally built them with a gamegen tool from a source tree (`data\` beside a tool folder of `.gs`/`.gw` scripts), repackaging shared textures, models, animations and resources for every mission. zStudio reconstructs that source tree from shipped files, lets you work on the sources, and builds every game file from them again: resource archives, scripts, sounds, interface images, texture packs, worlds and animations.

A source project is separate from editing ZBD files directly. Compiled files open only through MCP `open_root`, and their editing is being retired. In a source project, the sources are what you edit; game files change only when you export them. Exported files must work in the game; they are not byte-identical to the shipped files.

## Reconstruct, check and export

Source dependency checks distinguish a missing file from one that cannot be inspected. A locked or inaccessible script, model reference or source folder refuses the affected plan; restore access and retry. This also applies while checking another mission before changing a shared model's transform.

Cancellation is observed during script and resource text scanning, syntax materialization and script-edit verification, including long comments, quoted values and blank lines. Reconstruction reverses scripted hierarchy edits with indexed, ordered links and a shared work allowance; excessive work refuses reconstruction while retaining the original game files. The original child order and repeated-link semantics remain authoritative.

Source inventories also share a 128 Mi-unit allowance for complete path representations, retained rows and comparison work within an operation. This conservative accounting applies before retaining path lists or their projections, including build rechecks, effect discovery and publisher directory scans. Pending files share one frozen index through planning and rechecks; disk folders are still listed again to detect changes. Long shared prefixes still count for each materialized path; individual file-count limits do not replace this aggregate allowance. Exceeding it refuses the inventory with guidance to use shallower folders or fewer files, preserving complete identities rather than shortening or omitting them. Required recovery and best-effort cleanup have independent bounded allowances, so an exhausted request cannot consume the work needed to restore originals; cleanup may leave retryable remnants.

Animation-definition discovery shares its limits across the selected mission and every other mission it inspects: 64 MiB of source input, including repeated reads, 10,000 reads, 16 MiB per file, 64 Mi units of directory-probing work and a 16 MiB allowance for retained names, paths and collection storage. Missing-file probes consume work too. Reaching a limit refuses discovery with guidance to reduce the inputs; it never returns an incomplete list of animation choices. Complete names and mission identities are preserved.

Animation search paths retain their authored first-occurrence order with case-insensitive duplicate matching. Definition loading and keyframe resolution share a 64 Mi-unit allowance for directory normalization and candidate construction, including unsuccessful lookups, with cancellation throughout. Texture-script preview searches likewise share bounded node/edge work; an exhausted allowance produces an explicit incomplete-preview diagnostic.

Source-save planning reserves a conservative 128 Mi-unit path-work allowance before expanding paths or checking their filesystem state. Deep paths shared by many files reuse their directory prefixes. Recovery applies the same allowance to every journal file and recorded cleanup folder before expanding their paths; discovery shares it across all journals, and direct resolution checks its selected journal. New saves also admit their cleanup folders so they cannot produce a journal beyond the recovery allowance. An excessive save is refused before creating its staging area; an excessive recovery request leaves sources and journal history unchanged. Reduce the number or depth of changed paths before saving; for an existing journal that cannot be inspected, follow the recovery error without discarding its held originals.

Recovery also checks manifest collection counts and decoded string lengths before constructing its typed records. Escaped paths consume the same path allowance as their decoded forms, and repeated JSON fields cannot reset the admission counts. A refused manifest leaves its held originals and journal history intact.

Repeated world-node searches share a 64 Mi-unit node/edge work allowance within assembly, decomposition or lookup inspection. Names are cached without shortening their stored identity; renaming, deletion and slot reuse invalidate the assembler's cache. Exceeding the allowance refuses the operation with simplification guidance. Runtime lookup-script discovery also bounds distinct source inputs to 64 MiB and four million tokens before decoding or token allocation.

Script tracing lists directories by the engine's search-path rule ([Building worlds](#building-worlds)); traces outside a build (reconstruction and object edits) take every folder a script names as present, as the original build tree had them, which finds the same files. It retains bounded directory history across the complete reconstruction. Model and texture snapshots share an allowance of 4,194,304 reference-sized units, including array overhead; an unchanged search order reuses its previous snapshot. Directory parsing, normalization and search-order changes also share a 64 Mi-unit work allowance, checked before splitting or scanning. Excessive history or work is refused before copying, with a request to reduce directory changes or split the project into fewer missions. Source-object transform checks share these allowances across the nodes and missions examined by one operation.

Executed script operands have a separate shared allowance of 4,194,304 reference-sized units, including argument-array and instruction overhead, and 64 Mi units of authored and expanded text work. These limits apply before allocating repeated argument arrays or copying expanded macros, including across missions in reconstruction and cross-mission transform checks. Reaching a limit refuses the operation; full operand identities are preserved. Missing and empty model loads obey the same world-node capacity as ordinary object creation.

Cross-mission ownership checks for one object edit or model update also share an inspection allowance: 16 MiB per script, 64 MiB of distinct script bytes, four million tokens, one million physical lines and 64 Mi work units. Repeated graph scans still consume work, while unchanged parsed scripts are reused. Byte limits apply before reading or cloning pending content and before verifying a cached baseline. Exhausted limits and unreadable files refuse the edit instead of treating an incompletely inspected mission as absent.

Models consulted by those checks share a separate 512 MiB allowance for their actual container bytes. Each read receives the remaining allowance before allocation, and repeated node checks reuse the admitted model bytes. The held stream's header admits plain JSON or the GLB JSON chunk against 32 MiB before full reading or prepared-file hashing; a valid GLB's binary chunk retains the larger container allowance. JSON and GLB still pass the shared structural validation; a filename alone does not determine the container type.

Reconstruction counts every traversed model-reference occurrence, including repeated paths through a shared node. It allows at most 200,000 visits per reference walk and 4,194,304 across the reconstruction, checking before collecting or descending into another occurrence. Exceeding either allowance refuses reconstruction instead of producing an incomplete reference list. Model imports and script texture registration also enforce the world's 4,096-texture capacity before adding a new identity; references to an existing texture remain valid at capacity.

World assembly, model import, script tracing, animation compilation and repeated source-object attachment diagnostics use bounded warning collectors. These shorten authored text before formatting it; the full text is still used for lookups and execution. Each collector limits messages to 1,024 characters, retains at most 1,024 warnings and 256 Ki characters, and reserves at most 1 Mi characters of formatting work, including duplicate warnings. The world assembler and its model imports share one collector; reconstruction script traces and decomposition share another across missions. Other reconstruction and editing notices can also appear in the enclosing report. Once a collector limit is reached, one explicit notice says that additional warnings were omitted; the diagnostic limit does not itself stop the build. Directory summaries show at most eight shortened paths and the number omitted.

The welcome screen's card **Work with source project** is how zStudio starts: under it, **Initialize** opens a dialog with the retail ZBD folder and a new or empty project folder (type them or use **Browse…**); **Initialize and open** becomes available once both are given, shows the reconstruction's progress, keeps the dialog open with the reason if a folder is refused (for example files that are not the original ones), and opens the project when it is done. **Cancel** stops a running reconstruction and removes what it wrote; pressed once the project is already written, it leaves the project in its folder unopened and says so. **Open**, like **File → Open workspace…** (Ctrl+O), opens an initialized project and refuses another folder in a message saying what is wrong with it (no `data` folder, no `gamegen` folder, a link, or an earlier source format). Projects using the former `meta/zones.json` sidecar format are refused: reconstruct a fresh project from the original ZBD files. Opening or building never migrates or rewrites those projects. MCP: `zstudio_source_reconstruct` and `zstudio_open_root` with `project`.

- **Export → Check source project** builds every game file in memory and reports failures and warnings without writing. MCP: `zstudio_source_export` without `destination`.
- **Export → Export all ZBD files…** builds every game file into a folder outside the project. MCP: `zstudio_source_export` with `destination`.
- **Export → Export ZBD file** lists the game files the project can build; choosing one exports only that file. MCP: `zstudio_source_export` with `outputs`, for example `["m1/zrdr.zbd"]`.
- While a check or export runs, a modal progress window opens over the workspace (which cannot be used until it ends): the game file being built, how many of how many, then the lookup check and the writing of the files. **Cancel**, Escape or closing it stops the run: an export canceled before it writes leaves the destination as it was, and one canceled while it replaces files finishes or restores them (what it could not restore is listed in Diagnostics or, from the map picker, in its result window). An MCP `source_export` shows no window; it is an operation the caller polls until it completes, and MCP changes wait (`busy`) while the window is open.
- `zstudio_source_status` lists the game files the project can build and the sources of each, and the project's build profiles.
- **Check and export report lookups by name.** The game finds some nodes by name as a mission loads: the texture-effect scripts' `FindNode` (`gamegen/mN_zbd.gs` and the scripts it sources, whose commands match as the game's interpreter matches them: case-sensitive, and up to `Quit`), each animation's root, its attach node when the root lacks it, the names inside an animation that neither the attach node's nor the root's subtree has, and the first node of each activation prerequisite path. Where several nodes share the name, the game takes the highest slot, the node made last. Check and export list each such lookup in Problems (Info) with the node the game finds. An export that replaces a mission's files also warns about every lookup that now finds another node than those files did. In a source world, an edit that does so is reported in Problems (a node the edit moved to another parent, found by the same lookup, is still the node it was: it is paired with itself by its source), until it is saved or taken back, and the edit's result counts these lookups (MCP `lookupChangeCount`); copying an object, for example, copies its parts with their names, and the copies are newer.
- **Tools → Compare worlds…** shows two worlds, such as a shipped `gamez.zbd` and an exported one, as one node tree merged by parent-child structure, whatever the order of their nodes (see [Known differences](#known-differences)). MCP: `zstudio_world_compare` and `zstudio_world_compare_tree`.

The general Check/export script-lookup report does not expand runtime macro operands and is not a complete report of every runtime binding. Terrain-conversion protection separately executes the selected mission's script contexts to preserve their expanded references. Whole-world name comparison also does not establish unchanged resolution within reordered duplicate-name subtrees.
- **Export → Build profile** chooses which texture packs exports and checks build (see [Build profiles](#build-profiles)). MCP: `zstudio_source_profile` changes the same shared choice; `zstudio_source_export` with `profile` overrides it for one export.
- **Export → Texture dithering** chooses how exports and checks convert texture colours (see [Texture dithering](#texture-dithering)). MCP: `zstudio_source_dithering`.

The **Export** menu (between Tools and Help) appears when the open folder is a source project, which is any folder with both `data` and `gamegen` subfolders. What it can build is derived from those folders; zStudio's own working data (save journals, save staging and Blender checkouts) lives in the project's hidden `.zstudio` folder, which builds never read; mission worlds are evaluated in memory (see [The .zstudio folder](#the-zstudio-folder)). Listing what a project builds walks its `data` and `gamegen` folders, and every file and folder there counts, whatever it is: a walk that would visit more than 250,000 is refused with a message naming the folder, so keep editor caches, backups and design files elsewhere. Cancelling a status request, check or export stops the walk.

When the destination already has some of the game files the export writes, the GUI names them and asks before anything is built. The export itself makes that list once it has planned its outputs, so it is exactly what it would replace: an export of every output names its automatic `rtexture` pack from the textures as their build counts them, which can be another pack than the PNG headers suggest. Only the files confirmed are replaced; declining cancels the export. MCP needs `overwrite`, which allows replacing any of the selected outputs; without it the export is refused and names the existing files. Without `overwrite`, a game file that appears in the destination while the export runs is not replaced either. Other files in the destination are left alone, so a game installation can be the destination. All outputs are built, reopened through the shared readers and staged first; if any output fails, nothing is written, and a check reports every output with its failure or warnings. Before anything is replaced, every staged file is checked against the bytes that were built and reopened, and held until it is in place so that no other program can write, rename or delete it: a staged file changed after its output was built fails the export, and nothing is replaced. Publication moves replaced files aside and restores them if a later step fails. Undoing it removes an output only while it still has the content the export installed and the destination's `.zstudio-backup-…` folder still holds the original it replaced: a file another program wrote at an output's name meanwhile stays, and the original stays in that folder, which the error names; if another program deleted or changed the original there, the output stays in its place and the error says so. A canceled export stays canceled, and says what it could not undo. Unsaved edits to project files, including additions to an open mission world, must be saved or discarded before exporting, because exports read the files on disk.

Exports check source content while reading, on repeated reads and again before anything is written; an edit made while an export runs fails the export rather than mixing two states. That includes the build profile and what planning read: before anything is written the export is planned again, and it fails when that gives other outputs, inputs or texture packs (a source added or removed, a texture whose new size names another automatic pack). Opening another folder cancels a running export.

Reconstruction supports RECOIL data and requires RECOIL evidence (prepared scripts, a version-15 world or a version-28 animation program). It reads the files the game reads: those in the chosen folder and in its mission folders (`m1`, `m2`, …). Files anywhere else, such as a demo copied into a subfolder, are listed as not reconstructed and decide nothing. MechWarrior 3 folders are refused, and so are the 1998 demos' folders (GameZ version 13 mission worlds), whose worlds and placements open read-only. A project is reconstructed once, from the original game files, and from then on only exported: zStudio unpacks only files whose resource archives carry the animation definitions every `anim.zbd` was compiled from, which the shipped ones do and zStudio's exports do not, and refuses any other folder with "zStudio can unpack only the original ZBD files." A canceled or failed reconstruction removes everything it wrote, so the same folder can be used again; files another program put in the folder meanwhile stay, with the folders that hold them. Reconstruction creates every file as new and never replaces one: a file another program creates at one of its paths during the run stops it, and stopping removes only files that still have the content it wrote, naming any another program changed. The game files must not change while it runs: it captures size, modification time and a content digest for every probed input before reconstruction, and a file that is no longer that file when its turn comes stops the reconstruction, which removes what it wrote. Projects and export folders can never be the protected `zbd_1998`/`zbd_1999` corpora, overlap their input (also when spelled through a short name, a SUBST drive or a link above the input), or pass through links. Text sources larger than 16 MiB are refused before they are decoded. Placing one family's sources needs the others' evidence, so reconstruction keeps the sound banks, texture packs, worlds (as decoded models), animations, decoded resources and scripts it reads in memory until every file is read; a folder whose files would keep more than 1.5 GiB that way (estimated per file; the releases need about 500 MiB) is refused, and what was written is removed.

## Mission worlds

In a source project, a mission's world is evaluated directly from its glTF hierarchy, GameGen scripts, ZRD resources, animation definitions, PNG textures and WAV sounds. Choose its map button to open it. The editor uses no intermediate ZBD files or preview cache folder. The shared world evaluator supplies the same geometry, flags, zones and mission layout semantics used by export, while textures retain their source quality. Missing or invalid optional resources are reported in Problems; an invalid authored difficulty resource remains unavailable rather than silently selecting another difficulty. A snapshot freezes its inputs: external changes during evaluation refuse publication, and later changes require reloading before editing.

### One workspace per project

The open map edits one set of pending changes, the project's workspace:
- **One history.** An edit can change several files, and missions can share a file, so Undo and Redo apply to the project's source changes.
- **One save.** **Save** writes every changed source file of the project together, and its tooltip lists them. `zstudio_source_changes` lists them too, with the history and a line diff of any file.
- **Evaluation.** Apply, Undo and Redo prepare a candidate source scene in memory before accepting the source transaction. Unambiguous glTF Position, Rotation and Scale edits update the accepted source snapshot directly, reusing geometry, resources and animation definitions instead of rerunning the full source loader. Initialization dependencies, script-driven transforms or structural changes use full source evaluation when necessary. Invalid changes or cancellation during preparation leave accepted content and history unchanged. If a later publication check fails, the transaction is taken back and its pending input remains available for retry. Once the document and scene accept the change, a later preview failure cannot retract it and is reported in Problems.
- **View updates.** Ordinary object and placement transforms retain the document, viewport, camera, geometry and textures, updating instance transforms, bounds and picking. Direct glTF transform updates preserve initialized child poses and visibility, and refuse reuse when movement would change initialization bindings or placement decisions. Source pickup identities use the same canonical resource paths as their edit store, so unrelated pickups do not force a scene replacement. Structural changes, ambiguous repeated occurrences and changes while VTOL analysis is open use a replacement scene with the camera retained. Evaluation and either presentation path create no archives.
- **Operation ownership.** While a source operation prepares or publishes, other edits, saves and reloads are disabled or report busy. Source history shares this guard with conversion planning. While a map opens, saves and interrupted-save decisions report that it is opening.
- **Reload** evaluates current dependencies and creates a fresh document and preview lifetime, including when the files are unchanged.
- **Closing and switching maps.** Only one map is open. Returning to Maps or choosing another map resolves pending drafts and asks whether to save or discard unsaved changes; Cancel retains the current map. MCP requires an explicit save or discard. A clean map stays open if preparation of its replacement fails.
- **Game export** reads the files on disk, so pending edits must be saved or discarded first. This is the only source-project operation that creates game ZBD archives.

Source edit admission counts unique retained file buffers against a 1 GiB allowance, including original files, pending content, undo/redo and prepared-edit rollback state. Replacement planning checks the actual old file lengths before reading their content. A refusal accepts no partial transaction and preserves existing history.

Edit admission also applies the save's path rules to every file an edit writes, whatever produced its name (an added or copied model, terrain, zones, the GUI or MCP): a name Windows reserves for a device (CON, PRN, AUX, NUL, or COM or LPT followed by a digit, with or without an extension, such as `aux.png`), a character Windows forbids in names, a trailing dot or space, or a name longer than 255 characters is refused when the edit is made, naming the file to rename. So is a path more than 1,024 folders deep, one whose full path Windows cannot create (32,762 characters with a drive letter) or too deep and long for a save to plan, and, from what is on disk when the edit is made, a file used as a folder, a folder where the file would be, a short (8.3) spelling of an existing name, or a file inside another file the project's unsaved edits write. Such a file can therefore never become a pending edit that blocks every later save of the project; Save keeps the same checks. A folder another program creates later where an unsaved new file would go is reported as a change on disk, so Reload asks to save or discard.

### Placements

Click a pickup, AI vehicle or AI network node in Whole world and change its fields, or show its handles with the card's Move/Rotate toggles, then **Apply** (a source world has no editing lock):
- Apply changes the owning resource tokens in memory: tanks use their selected AIV resource (for example `data\m1\zrdr\aiv.zrd`), while pickups use `puppies.zrd` and unambiguous matching difficulty records. Save writes those source files.
- Nothing else in those files changes: comments, spacing and other values stay.
- An integer coordinate that moves is written as a float, as in direct editing.

MCP: `zstudio_pickup_move`, `zstudio_scene_card`. Editing AI paths (Edit path, Tab) is hidden in source worlds for now; `zstudio_ai_path` remains.

### World objects

Every object of the built world knows the source that made it: a node of the mission master (`data\mN\models\mN.gltf`, including its embedded loader sections), a node of a model file, or the script instruction that loaded or created it, with the instruction that last set each property.

The selected object panel (or `zstudio_source_world_object`) shows its source, its position, rotation (degrees about Y, then X, then Z) and scale, and its flags:
- standable (altitude surface);
- collision (intersection surface);
- collide by bounding box;
- proximity;
- landmark;
- overwrite;
- CanModify (craters and quicksand allowed);
- ClipTo (craters and quicksand blocked; no script command sets it, so a script object shows it without offering it).

Only objects and level-of-detail nodes have these flags to edit: a world, light or camera node shows none, and an edit of its flags is refused. A flag set as it already is changes nothing (no line repeating it, no undo step).

CanModify and ClipTo are exclusive source modes. Enabling one clears the other in the same undoable edit; disabling the selected mode clears it. The same rule applies through GUI and MCP. An edit is refused when the source commands cannot express the required change without changing its established scope (for example, clearing a script-only ClipTo state, for which there is no script command). A source build also refuses a final state with both bits set instead of silently choosing one.

At exactly ±90° pitch, yaw and roll turn about one axis: the rotation then shows yaw 0, so an edit of the scale does not show another pair of angles for the same turn.

Editing them (or `zstudio_source_world_object_edit`) changes that source:
- **Database or model nodes:** a database node changes its glTF node's transform or engine flags, in the database file or in the part that holds it. A part is copied wherever the database references it, so an edit of a part applies to each copy, and Properties says so (`origin.part` in `zstudio_source_world_object`). A model file's node changes for every load of that file, and Properties says so. A script `Object3DRotate` or `Object3DScale` replaces a node's own transform with the script's rotation and scale (the engine rebuilds the node's matrix from them, keeping its position), so another copy or load that a script rotates or scales keeps the script's rotation and scale, which a rotation or scale edit notes, also where another mission loads the file: that mission's scripts are followed as its build runs them, finding the node by name (a `FindSubNode` below a load of the file, or a `FindNode` of the name once the file is loaded, which the note says may find another node). A node that a script itself rotates or scales is edited in those instructions. A copy whose script sets the edited flag keeps that value, which the edit notes.
- **Script-placed objects:** the instruction that set the value changes, for example `Object3DTranslate 110.0 5.0 -50.0`. A value no instruction set yet is added after the instruction that created the object.
- **Scripts other missions run too:** when another mission's world script also runs the script that set the value (such as a shared `world.gw` making the world, or `weapons.gw` setting its templates' flags), or, for a value nothing set yet, the script that created the object, the value is set before this mission's world is written instead, after a `FindNode` of the object (whose name must then be unique). Flag, transform and property commands set their values outright, so the last one gives this mission the value, and the other missions keep theirs. Deleting such an object stays refused: no line of one mission takes it out exactly, since a `DeleteTree` before the world is written would leave its nodes' slots in the world's node table, which a world that never made it numbers differently.
- **Refused:**
  - an instruction that runs more than once while the world is built, which would change several objects;
  - an instruction that takes its value from a macro.

  Edit those in the script.

**Copy, delete and move to another parent.** The object card offers **Copy…** (the copy's name) and **Delete**; moving to another parent is MCP-only for now; `zstudio_source_world_object_edit` has the actions `duplicate`, `delete` and `parent`. They apply to the whole object: a part of a model a script loaded stands for that load, and Properties names it.

| Object | Copy | Delete | Move to another parent |
| --- | --- | --- | --- |
| A node of the mission database or one of its parts | A copy of the glTF node and its descendants, beside it, sharing its meshes | The glTF node and its descendants leave the file | Moves in its glTF file, under another node of that file or to the world (a part's node: to the top of its part), keeping its place and its zone |
| An object a script loaded | The load is repeated before the world is written: `SetModelDirectory`, `LoadGameGen`, its flag and transform commands, `FindNode` and `AddChild` | Every instruction that loaded, changed or attached it, or a part its load made (wherever a script put it), becomes a comment (`# LoadGameGen …`), so the rest of the script runs as before | Its `AddChild` becomes a comment and a new one attaches it before the world is written; its transform changes so it stays in place. The scripts that made and attached it change, so each must run only in this mission, and no later instruction may lose it (below) |

**Applying edits and updating the view.** A draft previews the change; Apply validates its source transaction before accepting it in memory. Simple object, pickup and AIV transforms update the existing viewport instances, bounds and picking while retaining geometry, textures and camera. Changes that alter geometry, hierarchy or rendering resources replace the evaluated scene in memory and preserve the camera. While an edit takes longer than a moment, a card over the view names the step and its progress (**Applying the edit…** while it is prepared); the view darkens under it once it reloads: **Rebuilding the world…** while the whole world is evaluated again, then **Loading the rebuilt world…** while the rebuilt scene replaces the shown one. An incremental transform edit, which the view keeps, never darkens it. During a rebuild the sources differ from the shown world because of the edit itself, so no "Source file changed on disk" banner is raised meanwhile (and the banner gives way while the notice shows). The outliner keeps its open rows (found again by source file and glTF node, or by name for units and pickups) and scrolls back to a renamed group. Undo and redo evaluate their candidate state before changing accepted history. Save writes the changed owning glTF, GameGen, animation or ZRD source files, with external-change checks and verified publication. Moving an AIV tank changes only its placement scalars in the appropriate `aiv.zrd` and uniquely linked difficulty counterparts. Game export is the only operation that creates ZBD files and requires an explicit decision about unsaved source changes. `zstudio_preview_state` reports `reloading` only during scene replacement; source-world state reports `evaluating`, `sourceRevision` and bounded `diagnostics`.

**Rename and change the referenced model.** For an object of the mission database, Properties also offers **Name** and **Model**; `zstudio_source_world_object_edit` has the actions `rename` (`name`) and `model` (`model`, a project path such as `data/common/models/sonictur.gltf`), and `zstudio_source_world_object` reports the referenced `model`. A rename changes the glTF node's name (and engine name) in every copy of an instance or part holding it, and is refused while a script instruction finds the object by its old name, or while an animation the mission lists is bound to that name (a `NAME` list binds to the first listed name the world has: the shipped `destroy_turret` lists `tur_101` and binds to it in m1, and every turret uses that binding to hide its destroyed parts at load and to play its destruction) until the new name is added to that `NAME` list, or while the mission's animations, compiled with the new name, would be rejected by the game where they are not now (a definition that names the old name elsewhere, such as its `ANIMATION_ROOT_NAME` or an event's node, or a `NAME` pattern the new name matches whose other names the world lacks), which must be changed first; animations and resources (such as `ai.zrd` turret patterns) that name the object must be changed with it. **Model** changes the external reference the object holds, or that of its one referencing child (an OpenFlight placement such as `tur_101`'s `pturret.flt`, which is renamed after the new file), keeping the object's name, place, flags and zone; it is refused while a script acts on a part of the previous model or its holder, for a part of the mission database or a file a map references with zone assignments for its references (change those in Blender), and after the rebuild every script instruction must act on the same nodes as before; the placement's zone overrides for the previous model are removed, so the new model's nodes take its own zones (inheriting the object's). Both rebuild the world as one undoable change. Objects a script loaded are renamed or reloaded in their scripts.

**Rename groups the build removes.** Groups of the mission database (such as m1's `group1`, which holds `horizon`) and reference holders the build removes keep their names only in the sources: the build moves their objects into the world and deletes them, so the game never uses the name (a node slot the build left free keeps it as inert bytes; shipped worlds other than m6 reuse those slots). Right-click such a row in the world tree and choose **Rename…** (MCP: `zstudio_source_world_object_edit` with `action` `rename`, `sourceFile` and `gltfNode` as `zstudio_scene_tree` reports them). The glTF node is renamed in every copy as one undoable change; a name a node of the world or of its sources has, or a script instruction that acts on the node, is refused, and the rebuild must leave every script instruction on the same nodes.

Names are written into scripts and found by name, so a copy needs a name no node has, and a parent a script line finds by name must be the only node with it. **Copy…** places the copy beside the original (its X plus the object's width, keeping its rotation and scale) as one undoable change, as `duplicate` with `beside` does, and selects it. An object without a visible width (a Light, a Camera or an empty group) is copied in place, where `beside` refuses it. A copy of a part's node is made in every copy of the part; the card selects, and `duplicate` returns as `copy`, the one beside the node copied. A node the file places under several parents (an instance, such as the node holding 1999 m9's gate under sgate1–sgate8), or anything inside it, changes in every copy of the instance: the build reads its first copy, so changing that copy alone would let the others come back. Its transform, flags, copies and deletion apply to each copy (refused when an editor made the copies differ); it does not move out of the instance, which would keep one place, and nothing moves into one, which would place it under every parent (also when a script took the instance's other holders out of the world). An instance without a zone of its own takes the zone of the copy the build reads first: a move or deletion that makes the build read another copy writes the zone it had onto every copy (refused when that zone came from references to a part in different zones), and a copy of a node holding an instance keeps that zone too. A part referenced from inside an instance is one copy in its own file, so its nodes move within the part. Moving a parent across an inferred inline section is refused if it would split a shared descendant between independent load scopes; moving nonshared content or a complete self-contained section remains supported. Copying is refused while a script takes a part out of the object or acts on a part its file holds elsewhere (morfUtil.gw's morph LODs), and a node a script left with no parent moves only in the scripts. A level-of-detail node moves only under a parent standing where its parent does in its file (relative to their size; the top of a part stands where its references put it), and a move under or out of one notes that the object draws only within, or no longer depends on, its distance range. A script's `NodeSetLighting` lights everything below its node as the build has it then, so a move that would change which one reaches the object is refused. A group of the mission database moved where the build deletes it (to the top, or into such groups) must have no geometry and no transform, since its objects join the world. Deleting a script-loaded object also takes out what scripts did to its parts (a `FindSubNode` that found one only when nothing else was ever attached below it; a renamed part is no longer found by its new name). An object a script attaches elsewhere is copied in the scripts, as is a script-loaded object whose parts scripts change; nothing moves under a node a script took out of the world. Since the build finds nodes by name, a copy or move in a glTF file is taken back when its rebuild makes any script instruction act on another node, also a node the build frees again (the mission database's groups and root); so is a copy, move or deletion in the scripts when any instruction other than those it changes acts on another node or none, each compared as the line it was before the edit (an object moved out of a holder that a later `FindSubNode` searches is no longer found there, so the translation or flag the lines after it set would be lost); moving a node that holds a copy of an instance can make the build read another copy, which is still the same node, and a node inside an instance is known by its name among its siblings, so a copy made beside one leaves the others the same nodes. Script transforms hold no shear, so a script object does not move under or out of a turned parent whose scale is not uniform, and a node whose transform holds a shear or a zero scale keeps its rotation and scale; a scale of 0 (or below 0.00001) is refused, since it leaves no rotation to read back, and a move that would flatten a node or place it beyond ±1,000,000 of its new parent is refused. A move that would change a node's zone writes the zone it had; a part's node whose copies take different zones from their references cannot move where a zone of its file would replace them. The maps that bind the file follow the same rule: a node that takes its zone from the load, under new parents that take theirs from the load too, keeps taking it in that map; under new parents with a zone there, it states the zone every load in the shown build gave it, and the move is refused, naming the map, when its loads gave different zones (give it an object zone in the Zone section of its card in that map first). A template (a loaded model no node holds, which resources place copies of) cannot be copied or moved, and objects other instructions use (a camera's horizon, a world's light) cannot be deleted. Animations and resources that find a deleted object by name no longer find it; Problems lists what the rebuild reports.

**Out-of-date maps.** When a source dependency changes after the displayed map was built, including through undo, its node, line and resource references are out of date: edits made from it are refused until it is reloaded. Undo does not depend on them. Add model is refused too, since its rebuild is checked against the world as shown.

Fog, lights and cameras are set by script commands. Properties of the world, a light or a camera lists the commands that set it, for example `WorldSetFogColor 0.5 0.5 0.5`; changing one edits that instruction. The commands that fit the node but are not set yet are listed empty: entering their arguments adds the command after the instruction that created the node. `zstudio_source_world_command` does the same.

### Map zones in the source hierarchy

Reconstruction retains map attributes in the glTF hierarchy. The mission master keeps its original filename, such as `m1.gltf`, and links evidenced original model files using relative `extras.recoil.ref` paths. Every reference resolves to a physical source file. Objects authored inside a file stay inside it; identical geometry does not erase distinct original file identities. Uncertain loader sections stay embedded in their owner rather than becoming invented numbered model files.

Node zone words, independent altitude-probe gates and complete ordered polygon zone words remain embedded with the source data. CanModify and ClipTo retain their stored node-flag granularity; they are not converted into per-polygon flags. Referenced models retain their defaults; reference occurrences retain placement-specific differences, including nested references. A model can inherit a different zone at each placement. Unknown upper bytes and untouched polygon words survive editing. A polygon with no zones differs from one assigned to zone 255 (`Any`). These are authoritative build sources, separate from viewport settings; no external `meta/zones.json` owns these attributes. Old sidecar projects require fresh reconstruction from original ZBD files, without migration.

To read or change an object's zone, select it: the card's Zone section sets Inherit, Any or a zone number and the altitude zone check, applied with its other fields (see [3D inspection](scene-inspection.md)); `zstudio_scene_inspect` and `zstudio_source_world_object` report the built zone (as `Inherit (ID)` when the node inherits it), the gate and which node, placement or load root supplied the value. Polygon zones are painted with the source map's polygon zone tool (**Edit zones** in the Zones group, or Tools → Paint/Erase polygon zones; see [3D inspection](scene-inspection.md)): a stroke paints or erases one zone on every polygon of the map's own models (`data/mN/models`) it crosses, as one undoable change written into the owning glTF without rewriting geometry buffers. A placement of a model takes its own zones as its placement override; a file's own geometry changes wherever the file is loaded. Models in `data/common` (shared by every mission), mission vehicles in subfolders, placed units and pickups and editable terrain are not painted. Paint adds the zone after a polygon's others and leaves a polygon that already has three as it is; painting Any replaces a polygon's zones and a numbered zone replaces Any, as on every shipped polygon (Any never stands beside another zone there). Erase removes the zone; erasing the last leaves none, which differs from Any. The zone picker names zones; labels are stored in the map's master model. Strokes, their undo and label edits update the shown world in place; a placement whose zones come to differ from (or agree again with) the other placements of its model is evaluated completely. Save uses the source workspace's verified save and external-change protections. MCP: `zstudio_source_polygon_zones`, `zstudio_source_zone_tool`, `zstudio_source_zone_label`.

Terrain recipes retain their existing surface/region authority and viewport painting tools. Conversion reads effective embedded assignments and transfers polygon words to the new surface profile while remapping the remaining database. Structural object edits update the embedded attributes alongside their source nodes. External geometry edits must retain the polygon and node identities used by those attributes; a mismatched layout is refused rather than applying assignments to different geometry. The bundled RECOIL Blender extension preserves this hierarchy and its attributes; use its import/export commands with a graph checkout.

The [status record](status.md) lists the checks the polygon zone tool has passed and its remaining limitations.

A stroke takes at most 4,096 polygons (a longer one keeps its first and says so) across at most 1,024 placements (an MCP request with more is refused; a GUI stroke keeps the first and says so). For a map-owned object, its altitude-probe gate is edited through the zone service (the card's Zone section); the ordinary glTF flag editor refuses a gate write that the map would override.

### Terrain

Terrain is authored as unsplit surfaces in glTF plus a **terrain recipe** beside them (`name.terrain.json`). The recipe holds the gameplay attributes painted on the surfaces. The build cuts the surfaces into the pieces the engine needs.

- **Creating a terrain.** **Tools → Create terrain…** (or `zstudio_source_terrain_create`) takes a glTF file of the project and the meshes in it that are terrain. The surfaces must be in a file of their own, not in the mission database nor in a file it references (its parts, or a model its objects reference), whose nodes stay objects of the world. It:
  - writes the recipe, beside the file (`name.terrain.json`) unless the dialog's **Recipe** field (MCP `recipe`) names another project path ending in `.terrain.json`. Another name lets a second mission's terrain use the same surfaces file, or a terrain be created again while a recipe no world uses keeps the first name; an existing path or one outside the data folder is refused;
  - adds a marker node to the mission database's roots, whose `extras.recoil.terrain` names the recipe. The pieces take the marker's place in the root order. The marker is named after the recipe (`name_terrain`), or `terrain` when that would not be an engine name of at most 35 Latin-1 characters, numbered while another node of the database has the name.
- **What the build does** (the splitter):
  1. Cuts each surface exactly at the world's cell lines (`WorldOrigin`, `WorldExtents`, `WorldPartition` must come before the database load).
  2. Cuts along the outlines of painted regions, and gives each part the attributes of the layers covering it: the recipe's defaults, its surface's defaults, then the regions in order. A part is cut only where an outline edge itself runs through it (never along the edge's line beyond its ends), so painting adds about 1.3 polygons for each outline point over the terrain. Painting that adds more than 16,000 polygons (more than any shipped world holds in all) is reported when the world builds, since every polygon is drawn on its own; a terrain whose polygons, with the world's others, pass the 262,144 a world can hold is refused, naming its recipe.
  3. Groups parts into pieces by surface, cell and node attributes (zone, gate, flags). A piece is named after the recipe's file name (its first twelve letters, digits and underscores, numbered when another recipe of the world begins the same way), its surface and its cell.
  4. Divides any piece that would pass the engine's 921 vertices or normals, using exact finite positions and the emitted normal values as conservative capacity counts. Subdivision keeps the incoming polygon order instead of sorting by position; pieces may be less spatially compact within their cell. Import refuses any polygon the compiled model cannot retain. A crater-capable piece (CanModify without ClipTo) keeps the [crater limits](engine-evidence.md#craters-and-quicksand) instead: at most 450 vertices or normals, so the growth of a cell's 16 craters stays within the 922 the engine keeps, and polygons of at most 30 corners, counting the corners junction repair adds. A longer polygon is split along chords between its corners: an authored polygon into fans from its first corner, which draw the same triangles; a cut piece between corners on different edges.

  Every cut point is put into each polygon that shares the edge, so pieces meet without cracks or T-junctions. Cuts preserve the original polygon's triangle fan and its interpolated UVs. The engine takes a polygon's plane, for heights and collision, from its first three corners ([How the engine sees a map](world-editor-plan.md#how-the-engine-sees-a-map)), so every polygon starts on a well-shaped triangle (twice its area at least 0.001 of its longest edge squared, so the sine of each angle is too, and its smallest height at least 0.01): a cut piece, also one that crosses no layer outline, starts where the plane through its first three corners lies within 0.005 of every corner; a polygon whose first corners lie on a line (cut points on an authored polygon's first edge) is turned when it is a triangle, and otherwise gives up its leading triangle, with those corners, as a polygon of its own, so it draws the same triangles. An authored polygon the build neither cuts nor adds corners to is kept as recorded. Generated normals are interpolated through all cuts and normalized once at output, so earlier cuts do not change the direction at a later shared point; untouched authored normals retain their values. The same recipe and surfaces always give the same pieces.
- **Attributes:**
  - `zones` (one to three zone numbers, or `any`);
  - `nodeZone` (a number, `any`, or `auto`: the one zone a piece's polygons share, otherwise `any` with the gate on);
  - `nodeGate`, `collision`, `standable`;
  - `craters`: `allowed` (CanModify), `blocked` (ClipTo, "no clip") or `ignored`;
  - `soil`: default, water, seafloor, quicksand, lava, fire, or 6–99;
  - `priority`;
  - `flags`: an exact word of the node flags.

  An attribute a layer does not set comes from the layers before it. Attribute shapes and scalar representations are checked before expanding parsed JSON into editable nodes, including GUI/MCP patches: `zones` still accepts only one to three entries, enum spellings follow their listed values, numeric spellings use at most 256 JSON bytes, and a `flags` spelling uses at most 256 decoded characters. Excessive padding or malformed collections are refused rather than shortened.
- **Limits.** A recipe holds at most 64 MB, 256 surfaces, 4,096 regions, 1,024 polygons per shape and 200,000 points per ring (1,000,000 in all). Its JSON is measured before anything is built from it: at most 10 million tokens (a recipe at every limit holds under 7.9 million), and at most 65,536 under keys a recipe does not have, such as notes, which are read past. Edits keep those keys of the recipe, its surfaces, regions and shapes (after the recipe's own keys); keys inside a shape's polygons are not kept, since painting rebuilds the polygons. A recipe key given twice in one object is refused; keys a recipe does not have are kept as given, repeats included.
- **Regions** have a name, the surfaces they apply to (all when none are listed) and a shape: polygons with holes in plan view (x, z), optionally limited to a height range. A region without a shape covers its whole surfaces; **Cover nothing (paint it)** in Properties empties it so the brush can paint it (painting it while it covers everything is refused). Stacked sheets, such as a cave floor under its ceiling, must be separate surfaces: the engine's altitude probe takes the first polygon of a node.
- **Pieces are build output.** Properties of a terrain piece shows its recipe instead of the piece:
  - recipe and surface defaults;
  - the regions in the order they apply (select, move, delete, add, rename, choose surfaces, set attributes, make one cover its whole surfaces);
  - the **brush**: **Paint in viewport** or **Erase in viewport**, then drag over the terrain;
  - **Paint polygon** and **Erase polygon**: typed plan-view corners (`0 0, 10 0, 10 10`; a semicolon starts a hole) for exact edges the round brush cannot draw, as `zstudio_source_terrain_edit` `paint` with `polygons`.

  Each stroke adds or removes the area a round brush of the given radius covers, as one undoable change, and the world rebuilds. Escape drops a stroke in progress. Terrain painting and the polygon zone tool are mutually exclusive: starting terrain painting ends the zone tool, and is refused while a zone stroke is held or its strokes are still applying; engaging the zone tool turns off terrain painting. An active stroke must finish or be canceled before switching. MCP: `zstudio_source_terrain`, `zstudio_source_terrain_edit`.
  The viewport brush uses world coordinates in Whole world (including isolated objects) and generated terrain piece previews. Inspecting an unrelated model suspends the brush without losing its recipe, region or radius; returning to a supported preview resumes it. Replacing or clearing a preview cancels its unfinished stroke. MCP painting takes explicit world coordinates and does not depend on the selected preview.
- **Viewing.** The Whole world highlight modes show craters allowed (CanModify), no craters (ClipTo), non-default soils and **zones** (each surface in its node zone's colour, grey for any).
- **Convert to editable terrain** (**Tools → Convert to editable terrain…**, MCP `zstudio_source_terrain_convert`) turns a shipped map's hand-cut pieces into terrain:
  - **Which pieces.** The mission database's untransformed mesh objects (its roots, and the objects its transparent database groups hold) become surfaces beside the database. Uninterrupted runs of converted siblings get separate ordinary recipes, sharing `mN_terrain.gltf` and its binary file. The first recipe is `mN_terrain.terrain.json`; later recipes use distinct numbered prefixes so the compiler's shortened names remain distinct. Each marker replaces its own run in place, preserving encounter order around retained objects and groups. Pieces in the database's parts stay objects, because every copy of a part shares its file.
  - **Surfaces.** Adjacent pieces with the same node flags, effective zone, stored appearance and model values (lighting, scrolling) share a surface, except where they overlap in plan view: those go to separate surfaces, so stacked sheets stay separate nodes. A later piece never merges into a surface before an intervening piece. Every piece compiled from a surface takes its mesh's model values and its stored appearance, including inactive values and unknown flags. Different appearance records remain separate surfaces.
  - **What stays.** Every polygon keeps its corners, UVs, normals and material (with its zones and soil), and each surface gets its pieces' exact flags, zone and `recoil.appearance` values. A terrain surface can carry its own appearance. A surface beneath an appearance-bearing ancestor is refused because flattening that inheritance cannot preserve its behavior and stored values; keep it as an object or author the surface as a root.
  - **Kept as objects:** the horizon and other landmarks, transformed nodes and nodes with children, references and the database's parts, shared nodes, pieces that collide by their bounding box or are proximity nodes (both depend on a node's own bounds), facades, pieces with lens flares, and any piece a script, resource or animation names or matches by wildcard. A compiled resource names what its strings hold; a text source larger than 16 MiB is refused before it is decoded, since the names it mentions would be unknown. Sources naming more than 262,144 different words (or 4 Mi characters of them), or holding wildcard patterns of more than 256 Ki characters in all, are refused too (all the sources of the 1998 or 1999 release together name under 76,000 in under 700,000 characters, with under 6,000 characters of wildcard patterns). The plan is made off the UI thread (Escape stops it), and the dialog lists them with reasons before anything changes.
  - **Reference discovery.** Decoded strings in text and compiled resources and animation definitions obey the same name and wildcard allowances. If decoded-reference discovery exceeds one of these allowances, the entire plan is refused instead of using the partially collected references. Malformed text can still contribute its lexical words, but a capacity refusal is not treated as malformed syntax. Script references include operands expanded by the shared interpreter, starting from the mission's build and captured load scripts with their own macro state, following sourced scripts and conditions. Missing executed scripts or exhausted discovery allowances refuse conversion. Discovery reserves 64 MiB of script source, four million tokens and 64 Mi character-work units for executed operands; repeated operands count toward the work allowance.
  - **Expanded output.** Planning and applying a conversion check the complete surface output before copying model metadata or serializing it. Every selected piece counts, including pieces sharing one input mesh and unused vertices retained by that mesh. The check uses the glTF reader's aggregate binary, decoded-component, primitive, morph-target and accessor limits, plus a conservative 32 MiB JSON allowance including escaped metadata and indentation. A refusal leaves the workspace unchanged; convert fewer pieces or remove unused mesh data and metadata before retrying.
  - **Acceptance.** After converting, zStudio compares the altitude probe over the converted area in the world before and after: heights, polygon zones, soils, node flags and zones, searching each point's grid cell and the world's own list as the engine does. On the 1999 data, M1, M5 and M6 give the same results at every sample point (M1 converts 210 pieces, M5 136 and M6 97; the pieces in the database's parts stay). Searched per cell, the converted terrain also finds ground at a few points along cell edges (M1 39 and M5 3 of up to 676,000; none in M6) where an original piece overhung into a neighbouring cell that does not search it.
    Equal-height candidates retain each world's recorded encounter order (cell entries before overflow children), because the engine can select a different surface when that order changes. Physical heights determine ordering before the report rounds them to two decimals. This is a sampled comparison of candidate surfaces, not complete gameplay equivalence across runtime zone gates, water filtering and vehicle probes; unavailable ordering or exhausted work is reported as incomplete.
  - **What is lost:** the original piece layout and names, and possibly how many crater models a crater creates. Undo takes the conversion back.

Not yet:
- tilted region planes for walls;
- zone probe validation;
- texture page cutting for large painted textures.

### Models from other missions

**Add model** is unavailable in the GUI for now (**Tools → Add model to world…** is shown disabled until it moves to its new place); `zstudio_source_world_add_model` loads any glTF model of the project into the world, for example a vehicle that only another mission used:

The picker lists physical glTF model files in the project. Adding one loads its embedded default attributes and follows its nested model references, including overrides authored within that reference hierarchy. Selecting a model file does not copy placement-specific overrides from an arbitrary occurrence in another mission. Missing references or incompatible embedded assignments refuse the addition before the receiving mission changes.

- **Name.** Choose the model and its node name (the model's name by default).
  - Resources and animations find the model by this name; the dialog says when the world already has a node with it.
  - `AddChild` attaches the newest node with the name, so a placed model cannot use a name one of its own nodes has (the root node of `vtol.gltf` is `vtol`). Such an addition is taken back with a request to choose another name.
- **Not placed** loads the model as a root outside the world, as the shipped scripts load vehicle templates: resources such as `aiv.zrd` place copies of it by name (`ltank_01` places a copy of `ltank`). **Placed in the world** puts it at a position and heading (the orbit point by default).
- **Animations** lists the definition files other missions list with an animation for that name, such as `data\common\zrdr\enemies\ltank.zad` for `ltank`. Checked files are added to the mission's `data\mN\zrdr\anim.zad`, keeping its comments and layout.

The edit adds the lines the shipped scripts use to load a model, before the line that writes the world:

```
SetModelDirectory ..\data\common\models
LoadGameGen ltank.flt ltank
```

and for a placed model its transform and parent:

```
Object3DTranslate 3161.9 33.0 2593.2
Object3DRotate 0.0 -90.0 0.0
FindNode %worldName%
AddChild ltank_wreck
```

Exports of the mission then include the model's geometry and materials, every texture it uses in each of the mission's packs, and its animations.

`SetModelDirectory` moves no folder the mission's scripts have listed already ([Building worlds](#building-worlds)), so a folder searched before the model's can hold another file of its name. Such an addition, or a copy of an object (which adds the same lines), is taken back, naming the file the mission would load instead; rename the model to a name no earlier folder holds.

### Editing models in Blender

The portable application bundles the **zStudio RECOIL** extension for **Blender 5.2 LTS, Windows x64**, in `dependencies/blender/zstudio_recoil-0.9.3.zip`. Install it from disk through Blender Preferences → Get Extensions, then choose the portable `zStudio.exe` in its preferences. Select an imported object and open **Object Properties → RECOIL** for individual node flags, crater mode and zone fields with hover descriptions. The sidebar shares these values and provides reference-workspace actions. The format helper runs without a zStudio window and does not enable MCP access. See the [extension guide](../blender/zstudio_recoil/README.md) for the controls and workflow.

**Tools → Edit in Blender…** now chooses a source model or master map and checks out its complete reference graph from the current shared workspace. Import the checkout input using **RECOIL glTF**, edit shared model collections or independent placement zones, then use **Export RECOIL glTF** to write a completed generation into the outbox. Each original physical source file retains its identity and relative references. Node flags, zones, face assignments, load-root values and advanced engine properties remain embedded in glTF; no authoritative property sidecar is introduced.

**Tools → Update from Blender export…** (with a map of the project open; MCP `zstudio_source_blender_update` names its document) validates the complete generation and its file hashes, remaps placement profiles in the graph and other source owners, and applies one undoable project transaction. The GUI shows the outcome in a message box; its notes are listed in Diagnostics, which opens. Source files change only on verified Save. Explicit conflict consent is required for source edits made since checkout and shared texture conflicts; it cannot force invalid or incomplete metadata. An update may replace what earlier updates applied only when its export descends from them: the same Blender import, and an export the same Blender file made before (each `.blend` records the generations it exported; an export is an undo step, so that record and the editor identities it assigned are saved and undone together, and placement assignments in other files follow only this file's own generations). Another import of the checkout, or an older save of the `.blend`, starts from before those updates, so its export treats what they applied as edits made since checkout (a conflict needing consent, or, when placement geometry changed, a refusal until those updates are undone in zStudio, a `.blend` saved after them is reopened, or a fresh checkout is made), never silently undoing them. A no-op round trip leaves transforms as the source wrote them. Only current graph checkouts are listed. Obsolete flattened checkouts cannot be updated; create a new graph checkout instead. Ordinary Blender glTF exports are not accepted by this workflow.

The extension retains its exact baseline and images when a `.blend` is saved. Unchanged geometry uses the source representation. Edited polygons retain their boundaries only where those boundaries preserve the exported surface, normals, UVs, morph deformation and placement-specific zones. A face split in Blender takes the placement zones of the nearest face it was split from that has an assignment. Unsupported geometry or ambiguous provenance is refused before the completion receipt is written.

### Saving and recovery

Recovery verifies the original's content before restoring it, even when its size and timestamp still match. A missing or damaged held original leaves the installed file intact and reports a conflict. Links inside staging or recovery, including their held files, are refused. Recovery scans allow at most 64 MiB of manifest and event-log data together and 50,000 file rows across the journals. Publication and recovery use the same 250,000-folder allowance per manifest. Publication checks escaped manifest bytes and reserves event-log space before creating working data; repeated recovery failures do not append duplicate event facts or grow the journal indefinitely.

On Windows, saves and exports retain directory identities through creation, verification, publication and cleanup. Operations use those held directories instead of resolving mutable ancestor paths again. Whole exports retain the same destination across all files and their report. Prepared edits also check that the project root still identifies the physical project whose files were verified. These protections do not provide isolation against every metadata change: another program can turn an empty staged file into a link after its final regular-file check and before atomic rename. Detected changes are refused; that final metadata interval remains an unresolved limitation.

**Save** writes the changed files as one recoverable publication:
1. Each file is staged and verified in `.zstudio\staging`.
2. A journal in `.zstudio\recovery` records what the save replaces.
3. Each original is moved aside and its replacement put in place, unless another program changed or created the file meanwhile. The staged replacement is checked against the journaled content first and held until it is in place, so no other program can change it.
4. The journal is removed.

If anything fails, the files already replaced are put back. A file changed by another program since the workspace read it is never overwritten: the save stops and says which file. Each saved file is read back once the save is done; one another program replaced in the meantime is reported as changed on disk, and its new content is what the project shows.

Save also checks that changed map-zone profiles still describe their geometry, and that geometry changed through the map-aware editors still matches every map that assigns its zones. It uses the pending source edits together with the current files on disk, so a zone edit or terrain conversion saved by another editor while this workspace had unsaved changes cannot silently invalidate the other map. A mismatch refuses the save and keeps the unsaved edits; undo or discard the conflicting edit and reload before trying again. Compatible profile and geometry changes can be saved together.

A project that is a link (a junction or symbolic link) or lies below one is never edited or saved, since its files would be written into the folder the link leads to: **Open** (and `open_root` with `project`) refuses it, and opened as a plain folder (MCP `open_root` without `project`) its worlds, edits, saves and recovery are refused.

If zStudio or the computer stops in the middle of a save, opening the project reports the interrupted save (in Problems, and in a dialog). The dialog fits the current monitor's work area, with scrollable details and decision buttons that remain visible. File and conflict summaries show bounded previews and disclose omitted rows; recovery retains the complete file identities. It offers:
- **Roll back**, which restores the files as they were before the save;
- **Complete**, which finishes the save;
- **Keep files**, which leaves them as they are and moves the journal to `.zstudio\recovery\abandoned`;
- **Later**, which leaves the decision for now: the save stays listed in Diagnostics, and saving edits (or reopening the project) asks again.

A file another program changed since is left alone. A file is read to compare it only when its size is one the journal records, so a file another program replaced with something larger is reported as changed without being read. Until the decision, the project cannot be saved. The decision is carried out in the background while the workspace waits, as during a save; closing zStudio stops it between two files (or while it reads files to check them), and the save then still needs a decision. The check made on opening holds the project's save lock while it reads files, so a save meanwhile is refused until it finishes; opening another folder (or the same one again) or closing zStudio stops it. A save that finished but left its journal is only reported (a warning); the next save removes that journal, and its warning with it. MCP: `zstudio_source_recovery`, `zstudio_source_recovery_resolve` (an unknown save id is `invalid_argument`; a file missing while resolving a known one is `io_failed`).

Reload refuses files with both external changes and unsaved edits. The GUI's Reload first asks to save or discard when it finds such a file; the project's edits are dropped only after that Discard (with no change to the workspace since). A conflict that appears after a check that asked nothing refuses the reload, which asks when it is run again. Its diagnostic previews at most eight paths, with 256 characters per path and a count of omitted files; complete conflict identities and unsaved history remain intact. Source close, terrain creation and source initialization keep their decision buttons visible within the monitor's work area while lengthy details scroll. Shortened source-close path previews can be expanded to inspect the complete paths.

### The .zstudio folder

Everything zStudio writes into a project goes into one hidden `.zstudio\` folder beside `data` and `gamegen` (user decision):
- `settings.json` remembers how the project was last viewed (below);
- `export\` holds graph checkouts, completed Blender export generations and sealed updates; older flattened checkouts are not accepted;
- `recovery\` holds save journals;
- `staging\` holds files being prepared for a save.

Earlier versions kept the working data in a separate `zstudio\` folder (and preview builds in its `cache\worlds\`); it is no longer used. Resolve any save that 0.9.0 reported as interrupted with 0.9.0 first (its journal there is not read any more), move an unfinished Blender checkout from its `export\` to `.zstudio\export\` and export from Blender into its new `outbox` folder (a `.blend` remembers the old one; Blender's file browser hides the dot folder, so type the path), or check the model out again, then delete it. Mission worlds are evaluated in memory, so nothing is built into the project.

Builds never read the folder. Its working folders are listed like the sources: `recovery\` and `staging\` when saving or looking for an interrupted save, each counting every entry there, whoever put it there. One holding more than 250,000 is refused with a message naming it, and a cancellation stops the listing. A save also lists each folder on the way to the files it writes, counting their entries together towards the same limit. Leave the folder out when sharing a project. It is safe to delete when no save was interrupted and no Blender checkout is still needed (the remembered view and the project's texture dithering go with it; exports then use None until it is chosen again).

How the project was last viewed is remembered in `.zstudio\settings.json`: whether **Diagnostics** was shown or closed and its height, the mission **Difficulty**, and the export's [texture dithering](#texture-dithering). Opening the project restores them, whatever the app-wide defaults became meanwhile; a project viewed for the first time remembers the difficulty it opens at. A damaged file remembers no view (the project still opens), while an export refuses to guess its dithering. Only the workspace reads it; builds never do, and it is safe to delete.

## Build profiles

A build profile says which mission texture packs an export builds, with what texel budget and largest texture side. The game opens `rtexture<N>.zbd` for the texture memory its card reports (in MB), counting down, so the packs decide what quality each machine gets.

| Profile | Packs | Status |
| --- | --- | --- |
| `original` | What each mission shipped with: `rtexture2`, `rtexture4` (256-texel textures), `texture2` and `texture4` everywhere, `texture6` in m1–m6 and m13, and `texture8` in m6 alone | Measured |
| `modern` (default) | `rtexture2`, `rtexture4`, `texture2`, `texture4` and `texture6` in every mission, plus `rtexture8` and `rtexture16` (up to 1024 texels), the automatic `rtexture<N>` when a mission's textures outgrow `rtexture16` (at most 256 MB), `texture8` and `texturemax` | Experimental until measured in the game |

`texture8` and `texturemax` serve only the software renderer; Direct3D, which every modern setup uses, loads `rtexture` packs. So larger textures reach Direct3D through the automatic pack: when a mission's textures at full size need more texture memory than its largest fixed `rtexture` pack, the export adds `rtexture<N>.zbd`, N that memory in MB rounded up to a power of two. It holds every texture at full size, up to its largest side. Above its budget (256 MB in `modern`, because the game is a 32-bit process) it is `rtexture<budget>.zbd`, the textures are reduced to fit, and the export says so. Planning and every pack's budget count a texture alike: two bytes a texel (one when paletted) at the size the pack stores, and a byte a texel for its alpha plane. An export or check of every output names N from the textures as the pack's build counts them: every texture it holds, with those its world brings from other missions' folders, and their alpha planes, learned by decoding each PNG once for the export. Listing the outputs, or exporting only some, names N from the PNG headers of the mission's texture folders alone, which cannot show alpha planes or the world's other textures; so the pack the profile promises at full size (the automatic one, or `rtexture16` when none was planned) may have to reduce some textures, and its build then names them with both sizes, and an export of every output adds the larger automatic pack. A pack never holds more than its name. The game skips a pack whose N is above the texture memory the card reports.

Either way, the textures come from the project's PNGs, which reconstruction takes from each texture's largest copy in any pack (see [Textures](#textures)): in m6 that is often `texture8`, the only pack that holds 100 of its textures at full size.

A project can add or replace profiles with files in `gamegen\build-profiles\` (builds never read them otherwise); the file name is the profile's name, and one may be the default:

```json
{
  "format": "recoil-build-profile",
  "version": 1,
  "status": "experimental",
  "default": true,
  "description": "Larger textures for modern cards.",
  "texturePacks": [
    { "file": "rtexture2.zbd", "budgetMiB": 2, "maximumDimension": 256 },
    { "file": "rtexture32.zbd", "budgetMiB": 32, "maximumDimension": 2048 },
    { "file": "texture6.zbd" },
    { "file": "texture8.zbd", "missions": ["m6"] }
  ]
}
```

- `budgetMiB` is the pack's texel budget (textures shrink to fit it); `null` keeps every texture at full size. Omitted values come from the pack's name, as before.
- `"file": "rtexture*.zbd"` is the automatic pack described above. Its `budgetMiB` is the largest pack it makes, a whole number from 1 to 1024 (default 256).
- `maximumDimension` is a power of two from 8 to 4096, and at most 1024 for the software packs (`texture<N>`, `texturemax`): the software renderer does not draw wider textures.
- `missions` limits a pack to some mission folders (`["m6"]`); without it, every mission gets the pack.
- A profile lists at least one `rtexture` pack without `missions` (the automatic one counts), so that every mission gets one: the Direct3D renderer reads only those, and without one it falls back to the software packs and refuses them.
- A file that cannot be used (one written before a rule above, say) blocks only itself: Export → Build profile shows it with the reason and `zstudio_source_status` lists its `error`, and only an export with that profile fails. When it may be the project's default (it says `"default": true`, or its JSON cannot be read), the default cannot be chosen, so exports without a profile fail until the file is fixed.
- Export results and `zstudio_source_export` name the profile used. When the destination already holds an `rtexture` pack the profile does not build, the export warns: the game picks packs by size and could load that one instead. The destination is checked before anything is written; one whose folders cannot be listed gets a note instead.

## Texture dithering

The texture packs store 16-bit colour: RGB565 texels in the Direct3D packs (`rtexture<N>`) and the software packs' direct textures, and palettes of RGB565 colours in the software packs (`texture<N>`, `texturemax`). **Export → Texture dithering** chooses how an export or check converts each PNG's 8-bit channels to them:

| Choice | What it does |
| --- | --- |
| **None** (until another is chosen) | Each texel rounds to the nearest stored colour on its own; smooth gradients can band. |
| **Ordered** | A fixed 4×4 threshold pattern spreads each texel between its two nearest colours. The pattern belongs to texel positions, so textures that tile stay seamless; up close it shows as a faint regular grid. |
| **Error diffusion** | Floyd–Steinberg: each texel's rounding error passes to the texels after it. The smoothest gradients, as fine noise; a tiling texture can show a seam where it wraps. |

Dithering changes only what the stored colours cannot hold: a colour the pack stores exactly (the game's expansion of a 565 colour, as in a texture reconstruction extracted) keeps it, so in the RGB565 (`rtexture`) packs a texture made only of such colours is built the same with every choice (error diffusion still spreads the error of other texels into it). A paletted software pack stores exactly only the colours its page palette holds (each page quantised to at most 255 colours), so a reconstructed texture there can change with the choice. A colour-keyed texture stores green at five bits, so its odd six-bit greens (as in two retail textures) are dithered like any other colour it cannot hold. Texels a texture does not show (keyed out or fully transparent) are not dithered, the key colour is never produced by it, and alpha planes keep their 8-bit alpha. For paletted textures the pattern's strength follows the spacing of the page's colours. In paletted textures, error diffusion carries at most 32 per channel into a texel, and a texel that error would move more than 48 from its own colour in any channel keeps its exact entry (or takes the entry nearest its own colour); it searches the page for the unrounded target, so colours at a channel's limit, like pure red, keep their hue. `image.zbd` (interface images) is not dithered. The result is deterministic.

The choice is the project's (user decision): zStudio keeps it in `.zstudio\settings.json` (see [The .zstudio folder](#the-zstudio-folder)), which only the workspace reads, and passes it to each export and check; builds never read the `.zstudio` folder. The MCP results of `zstudio_source_export` and `zstudio_source_status` name it (`textureDithering`); the Export menu's check marks show it. Direct3D still converts textures with alpha to 4444 itself when the game loads them; dithering cannot reach that step.

## Layout

```
<project>\
  gamegen\                     the original tool folder: *.gs and support\*.gw, recovered from interp.zbd
  data\                        the original source tree
    common\zrdr\{enemies,explosns,lighting,vtol,weapons}\*.zrd
    common\multi_bft\{zrdr,model,textures}\
    common\{models,textures}\  common\effects\{models,textures}\
    common\sounds\*.wav         common\{fonts,images}\*.png
    mN\models\*.gltf/.bin       mN\models\bft\     (the mission database mN.gltf and its loads)
    mN\textures\*.png           mN\textures\bft\
    mN\zrdr\{aipath,envmodels,vtol,bft,choppers,…}\*.zrd, *.zad, *.zan
    mN\images\*.png             (objective images)
```

Directory placement is recovered from evidence in the shipped files; [recoil-original-worktree.md](recoil-original-worktree.md) reconstructs the complete original tree from it. Every ZAR member records the temporary file its compiler created in the source directory (for example `D:\battlesportdev\data\m1\zrdr\envmodels\fueE3B0.TMP`), so each resource returns to its original folder, including subfolders that member names do not carry. Sound banks carry no source paths; their WAVs go to `data\common\sounds`, the `SOUND_PATH` set by `sounds.zrd`. The prepared-script index names each script (`support\common.gw`, `m1.gs`) and its modification time, which the reconstructed file keeps.

Animation definitions are `.zad` files: each mission's list (`data\mN\zrdr\anim.zad`) and every file it names, in the folders the shipped archives recorded. The original build kept them as `.zrd` beside the resources and packed them into `zrdr.zbd`, although the game never reads them there; reconstruction renames them, and the names in the lists with them. `pickup.zrd`, the one shipped file holding both, keeps its `PICKUP_DATA`, which the game reads, and its pickup animation becomes `pickup.zad`.

Exported archives record each member's project path (`data\m1\zrdr\envmodels\fuel.zrd`) where the original compiler recorded its temporary file. That field holds 63 Latin-1 characters (the shipped paths have at most 55), and placement edits in a built world find the source they change through it, so a resource whose project path does not fit fails the build of its archive rather than recording part of the path; the sound banks, whose field nothing reads, leave such a path out. Where the original compiler recorded when it packed an archive, every member of an exported archive or sound bank records the same fixed time (1 January 1980, 00:00 UTC), which the engine does not read, so the same sources export to the same bytes at any time and in any time zone.

## What is built

| Game file | Sources | Build |
| --- | --- | --- |
| `zrdr.zbd` | `.zrd` files in every `zrdr` folder under `data\common` | compiled, ordered by source path |
| `mN\zrdr.zbd` | `.zrd` files under `data\mN\zrdr` | compiled, ordered by source path |
| `interp.zbd` | `gamegen\*.gs`, `gamegen\support\*.gw` | tokenized; each script records its file's modification time |
| `soundsh.zbd`, `soundsm.zbd`, `soundsl.zbd` | `data\common\sounds\*.wav` | converted to the HIGH/MED/LOW formats of `sounds.zrd` |
| `image.zbd` | `data\common\fonts`, `data\common\images`, `data\mN\images` PNGs | interface images at their authored size in direct colour |
| `mN\rtexture{2,4,8,16}.zbd`, `mN\texture{2,4,6,8,max}.zbd` | the mission's texture folders, and every texture its world uses from elsewhere | each PNG scaled and converted to the pack's budget and colour mode |
| `mN\gamez.zbd` | `gamegen\mN.gs` and the scripts it sources, glTF models, texture names | the build script run with the engine's interpreter rules |
| `mN\anim.zbd` | `data\mN\zrdr\anim.zad`, the `.zad` definition files it lists and their `.zan` scripts | compiled against the world this export builds |

Archive members are found by name, so two sources with the same file name in one archive are refused. The game opens a resource from the first archive that holds its name and mounts `zrdr.zbd` before the mission's ([Engine evidence](engine-evidence.md#resource-archives)), so a mission resource named like a common one (a `data\m1\zrdr\vehicle.zrd` beside `data\common\zrdr\vehicle.zrd`) is never read: its archive still builds, with a warning naming both files. The shipped archives have no such pair once their animation definitions are `.zad` files. A `.zrd` source may be text or compiled data.

Each sound's source is its best-quality version across the three shipped banks. `sounds.zrd` declares a rate, sample size and channel count for each bank; the declaration is a ceiling. As in every retail bank, each of the three values is the lower of the source's and the declaration's, so a sound is never raised in quality. Conversion mixes channels, reduces sample size and resamples with a windowed-sinc low-pass filter; cue markers, which the engine turns into playback times, move with the samples. A sound is converted a block at a time into its result, so a long sound is held only as its source and result; a rate drop of more than about 32,000 times (a source of tens of megahertz) on a sound of over a million frames is refused. A WAV that `sounds.zrd` does not declare goes into every bank unchanged, with a warning. Only 8- and 16-bit PCM can be converted.

On the 1998 and 1999 retail data, the exported archives contain the shipped resources with identical compiled data, without the animation definitions (and `pickup.zrd` without its pickup animation); a `.zrd` source that holds animation definitions fails the export. The exports also have `interp.zbd` with the same scripts and tokens, `soundsh.zbd` with the shipped sounds unchanged, the medium/low banks with the shipped formats with the same frame counts (within two frames) and cues, every world the shipped nodes, placements, models and textures, and every `anim.zbd` the shipped entries.

Reconstruction lists shipped files whose family it does not reconstruct. They are not copied into the project.

### Textures

Each texture becomes one PNG from its best-quality stored variant in the folder the mission packs' record order places it: `data\common\effects\textures`, `data\common\textures`, the mission's `textures` and `textures\bft`, or `data\common\multi_bft\textures` for multiplayer missions. The best variant is the largest stored copy. A pack short of room sometimes stores a texture resampled to another shape of the same area (m5's `swall3` is 128 × 128 in `rtexture2` and `texture2`, 256 × 64 in `rtexture4`, `texture4` and `texture6`), so among copies of that size the shape kept by the pack with the most room wins: the larger budget (`texturemax` has none) and, at equal budgets, the software pack, whose paletted texels take half the space. The shipped packs rank `texture8`, `texture6`, `texture4`, `rtexture4`, `texture2`, `rtexture2`, and wherever a mission's packs disagree at the largest size, the higher ones hold the wide or tall shape. Among copies of that shape, direct colour is preferred over a palette. Packs are built from the PNGs on export: hardware packs (`rtexture`) as RGB565 with an alpha plane, software packs (`texture`) with shared palettes, except that the damage masks the mission's scripts register and the textures of the horizon (the world's `horizon` node and the cameras' horizons, which the game keeps at the camera) stay in direct colour, which the software renderer draws without shading or fog, as the shipped packs keep them ([Engine evidence](engine-evidence.md#textures-and-the-rendering-target); the few textures the shipped packs also keep direct by hand, such as the player vehicle's `tanktop` and `tankback`, are paletted, see [Known differences](#known-differences)). Besides the shipped 2 and 4 MB packs, exports add `rtexture8`/`rtexture16` and `texture8`/`texturemax`, which the engine loads when the card or the TextureMemory setting allows, so modern cards get every texture at full quality. A texture's edge mode (clamp or wrap) comes from the glTF samplers that use it. A texture no model samples takes the mode of the material a texture cycle shows it on, since the game draws every frame with its own mode: a `CycleTextureSetMap` frame of the texture-effect scripts the mission script runs after writing its world takes the sampler of the first material of the node that `FindNode` and `FindSubNode` select (the highest slot of a name, as the game finds it; a `CycleTextureSetOn` after a `FindNode` that found nothing leaves the previous cycle current, so the frames that follow join it while it has room, as in the game), and a frame in the `MAPS` of an `effects.zrd` effect that of the first material of the first model at or below the effect's node. To change such a frame's mode, change that material's sampler; a frame that cycles show on materials sampled with different modes fails the build. Other textures only scripts name (`LensFlareTexture`, `TextureAdd`, `WriteTextureSetMap`) repeat. Each texture command names its texture with its first operand (`LensFlareTexture` with the one after its stage number) and ignores any further operands, as the game's interpreter reads it. Reconstruction gives a cycled material whose own texture no pack holds (1999 m9's `surf`, which samples `surf00`) its frames' shipped mode, so every frame of both releases gets its shipped mode back. A PNG that decoders read differently is refused rather than read one way: chunks out of the PNG specification's order (a palette or `tRNS` transparency after the image data, `tRNS` before the palette, image data split by other chunks) or repeated, and a `tRNS` chunk of the wrong length for its colour type (2 bytes for greyscale, 6 for RGB, at most one value per palette entry), which would otherwise leave the image opaque; a transparent grey or RGB value uses only its sample's bits, as the specification states. A pack holds at most 4,096 textures, and its file at most 512 MiB. Each texture is stored at a size that follows from its PNG's header (up to 4096 × 4096), the pack's largest side (256 for `rtexture2` and `rtexture4`, 1024 for the other built-in mission packs, up to 4096 for a profile's `rtexture` pack; interface images keep their authored size) and, under a budget, every texture's transparency, since alpha planes count against it. So a build decodes one PNG at a time and keeps each texture only at its stored size, four bytes a texel, and keeps at most 256 MiB of them between its passes (palette colours, then writing); a texture beyond that is decoded again for each pass, with the same result: high-resolution sources and large packs cost time, not memory. Resampling a decoded PNG to its stored size works a source row at a time, so besides the PNG and the texture being made it holds only a few rows of workspace, never the image as floating-point values. Each PNG's transparency is learned once per export, when it is first decoded; under a budget, a texture that the budget then reduces further is decoded again to be reduced from its source. A pack with more textures fails before any image is read; a pack without a budget whose textures at their stored sizes exceed 512 MiB fails before any image is decoded, and one whose textures, fitted to a budget above 512 MiB, still exceed it fails once its textures are classified; both name the largest textures the pack stores.

Texture-pack warnings bound authored names and paths before formatting and share an aggregate diagnostic allowance. If it is exhausted, the pack's warning list starts with an omission notice; an enclosing build report can precede it with other output notes. Undeclared-sound warnings use the same bounded collector and place any omission notice first. These bounds affect diagnostics only; complete identities, ordering and output data are retained.

Export lookup-change notes and failure summaries also bound authored operands before formatting and limit aggregate diagnostic text. Lookup notes are prepared before publication, with cancellation checks; complete lookup records remain available in the report. Problems displays bounded warning previews and states how many retained entries it omitted. Report warning and note counts describe retained diagnostics, including any notice that the producer's diagnostic allowance was exhausted.

### Worlds and models

Numeric values that the glTF importer interprets may use at most 4,096 UTF-8 bytes per numeric spelling. One model read also shares a 64 MiB numeric-work allowance, including repeated reads of shared accessor, buffer-view and sampler fields. These limits apply before numeric conversion; decimal and exponent forms must still represent an exact integer where an integer is required. Unknown numeric metadata remains unchanged and available for explicit export under the existing JSON and metadata limits.

Node-lookup reports reuse structural fingerprints across targets that share descendants. Computing fingerprints and paths spends the same cancellable work allowance as the other lookup checks. If the complete check exceeds that allowance, the operation reports that lookups could not be checked rather than publishing a partial set of checked results. Full names, duplicate occurrences and child ordering retain their existing meaning.

Repeated-name lookups always go through the shared semantic world comparison: matching slots, name paths and structural fingerprints can still identify different instances under different parents or with different geometry. An unchanged or indistinguishable copy produces no lookup-change warning. The source-edit baseline decodes its world once when comparison is first needed and reuses it for later checks.

Numeric glTF indices and engine identity fields accept exact whole-number decimal and exponent forms, such as `3.0` and `3e0`; fractional values are never rounded into an index. GLB files must have exact length, aligned complete chunks, one initial JSON chunk and at most one BIN chunk directly after it. Triangle lists must contain complete triangles, and node rotation quaternions must be unit length. A node's morph weight overrides the mesh default; RECOIL supports one morph target per model, so additional targets are refused. Textured materials with an RGB base-colour tint require that colour to be baked into the PNG, because the game cannot preserve that multiplier. PNG end chunks must be empty and final.

Building models and terrain pieces shares the GameZ reader's total geometry limits across the world. The writer checks those limits and the complete output size before allocating its output, including point records and nested node references.

A model holds at most 921 vertices. The build merges a mesh's corners that lie within 0.001 units of each other, as the original build's AddOrMergeVertex did (retail 0x482720, which stops past 0.9 × 1,024), and refuses a mesh that still needs more, naming its node, mesh and counts, rather than build it without the polygons past the limit; no shipped model of either release exceeds it. Split such a mesh into several objects or reduce its vertices while preserving its source attributes. An added model or another edit the world cannot be built with is taken back with the same reason. Terrain surfaces are not models: the build cuts them into pieces below the limit ([Terrain](#terrain)). Normals merge within 0.0001 into at most 921 per model too; polygons past that are stored without normals (drawn flat), with a warning.

Shape keys must contain position deltas only. Morph normal or tangent channels cannot be stored by RECOIL and are refused; disable those channels in the glTF exporter.

Embedded base-colour images must be saved as external PNG files before import. All materials and loaded models that use one texture name must agree on its repeat/clamp modes; conflicting modes fail the build, as do texture cycles that show one frame no model samples on materials with different modes. A texture-only export also fails if its mission world cannot assemble, since the world determines additional texture dependencies and addressing. The glTF reader checks every node for cycles and excessive depth, including components outside the selected scene.

Build snapshots include files that were searched for but absent, such as optional animation definitions and preferred model search candidates, and the search folders a script names that do not exist ([Building worlds](#building-worlds)). If one appears before publication, the export is refused. A preview retains those missing inputs too, so their later appearance, or a pending file added below a missing search folder, requires reloading before editing. Pending workspace files count as present, and make their folders exist. Files actually read are rehashed before publication, so a same-length edit with a preserved timestamp is still a conflict. Source scenes retain those hashes for off-thread stale-input checks before preparing source edits. They also retain the common and mission resource inventory, including empty folders: adding or removing a resource can replace a difficulty fallback or shadow a mission member. Off-thread checks before and after edit preparation require reloading when that membership changes, including pending source additions.

The 8:1 texture aspect limit applies only to hardware packs. Software packs retain wide or tall images within their 1024-texel size ceiling and selected budget. Shared software palettes retain a near-black opaque entry separately from the zero transparency key. Reconstruction checks differing duplicate texture payloads within each mission pack before choosing quality variants across packs, including external palette content. Interface images remain separate when their recorded source folders differ; differing copies assigned to the same folder are refused.

A mission world is built by running its script, `gamegen\mN.gs`, as the original build did: the interpreter follows `source`, macros and `ifdef`/`ifndef` (a condition holds when its macro is exactly `TRUE`, conditions combine with `||` and `&&`, and while a block is skipped the first `endif` ends it, as in the retail interpreter), and applies the world, camera, light and node commands with the retail engine's semantics. `LoadGameGen name.flt node` loads `name.gltf` (or `.glb`) from the first of the model directories the scripts set with `SetModelDirectory` that holds it, in the engine's search order: a new folder goes first, and a folder named again keeps its place ([Building worlds](#building-worlds)); the file after `GameGenSetWorld` is the mission database, whose top-level nodes join the world. When the script writes the world (`GameZWriteZBDFile`), zStudio runs the engine's update (matrices, bounds, grid partition, single-parent flags) and writes version-15 GameZ.

Models are glTF 2.0 with PNG textures and zStudio reference/attribute extras. Source-project Blender round trips use the bundled RECOIL extension. A mesh placed under a mirroring transform (a negative determinant along its node path, such as Blender's Mirror) has its polygons turned over on import, keeping each polygon's first corner, because the game culls by the transformed winding and has no handedness rule; export turns them back, so the game shows the side glTF viewers show. A glTF mesh used with both handednesses becomes two models, and a node shared by parents of both handednesses is refused. Textures are separate PNG files (embedded base-colour images are refused; save them as external PNGs, including when the model geometry is in a `.glb`). A file's buffers may hold 512 MiB together (at most 4,096 of them; a buffer file listed again is read once), a node transform must be a 16-number `matrix` or 3/4/3-number `translation`/`rotation`/`scale`, not both, and a reference to a mesh, material, texture, image, sampler, scene or root node must name one the file has: anything else is refused rather than read as no transform or no reference. Accessors must hold what they are used for: positions, normals and morph target positions are floats and texture coordinates floats or normalized unsigned 8/16-bit integers; a file that declares `KHR_mesh_quantization` may also use that extension's 8/16-bit integer positions and texture coordinates, normalized signed normals and signed morph target positions. Every attribute has one value per position, and indices are unsigned integers that are not normalized (a float, signed, normalized or vector index accessor is refused rather than truncated or flattened). An accessor reads only its own buffer view (with its stride), sparse indices and values only their tightly packed views (which state no stride), sparse indices strictly increase, and a view lies within its buffer's stated `byteLength`: one that reaches further is refused rather than read from a neighbouring view's bytes. Data lies where glTF places it, or the file is refused rather than read from offsets other readers refuse: only vertex attributes have a stride, which is a multiple of 4 from 4 to 252 bytes that holds an element; the occupied accessor span, including its final element, must fit the view (indices are tightly packed). A one-element attribute can therefore have a stride larger than its view; an accessor, sparse indices and sparse values start at a multiple of their component size in their view, and the view at one in its buffer; and a vertex attribute's elements start on 4-byte boundaries of their view, so 8- and 16-bit vectors of another size (a byte normal's 3 bytes) are padded and given a stride, as `KHR_mesh_quantization` says. A material's base-colour texture is sampled with the texture coordinate set it names (`texCoord`) and its `KHR_texture_transform` offset, rotation and scale, applied to the coordinates as Blender's Mapping node does; another extension on that texture, or a file that requires an extension other than these two, is refused rather than read without it. Its sampler repeats (`REPEAT`, Blender's Repeat extension, and glTF's default) or clamps (`CLAMP_TO_EDGE`, Blender's Extend or Clip) the texture on each axis, which is all a RECOIL texture stores; mirrored repeat (Blender's Mirror extension or a ping-pong UV wrap) is refused rather than built as a repeat, which would tile it differently, and so is a wrap mode glTF does not define. The sampler's filters are not kept: the game filters every texture alike. Node hierarchies are trees: a node may have one parent, and a scene lists each root once. A file holds at most 200,000 nodes, meshes, materials, images, textures, samplers and scenes each, 1,000,000 accessors and buffer views each, 200,000 primitives, morph targets and weights across its meshes, and 32 MiB of names, extras and image paths together, unused entries included; these are checked before any entry is read. Engine attributes ordinary glTF cannot express live in `extras.recoil`:

- nodes: named flags described below, `zone` (a numeric ID from 0–254, `"any"` or `"inherit"`), LOD ranges, the `name` when a name repeats or looks like a Blender copy (`.001` suffixes are otherwise ignored), `ref` for an OpenFlight external reference (another glTF file, loaded under the node), `instance` for a node shared by several parents (glTF nodes have one parent, so each copy carries the same number and import joins them; the first copy is used), and `model` for a model without polygons (lens-flare points), which a glTF mesh cannot hold;
- Object3D nodes may also carry `appearance`: `flags` for the non-transform class bits, `alphaScale`, three-component `color`, and `colorAlpha`. These preserve inactive authored values as well as enabled alpha/color behavior. Transform bookkeeping bits (`0x39`) stay derived from the node transform. LOD nodes cannot store a local transform; a nonidentity transform on one is refused. Ordinary source loads use the first definition of an `instance`; later records join that node and may inherit different parent zones or omit its children. Source object edits check the copies they change before applying the same edit to each.
- meshes: display mode and flags, texture scrolling, morph factor, and point entries (lens flares);
- materials: polygon priority, back faces, `zones` as an ordered array of zero to three numeric IDs, colour, soil and the engine's material flags; textures by name (a material with an image uses the texture of the image's file name; the recorded `texture` names it only without one); `normals` when its polygons store normals (Blender writes normals for every surface, so a material without it stays flat);
- primitives: `polygons`, where joining triangles back into the stored polygons would not restore them (a count of fan triangles per polygon, or a corner list), and `polygonZones`, one zone-ID array per polygon, such as `[[3], [3, 7], []]`. Geometry with map zones records every polygon so its assignments retain their source identity;
- the scene: reconstructed sources mark `sourceFormat: 4`; `loadRoot` holds the named flags and `zone` of the node a script load creates. A load root accepts a numeric ID or `"any"`, but cannot inherit. The mission master's `zoneLabels` holds the editor's zone names.

Named node flags live directly in `extras.recoil`, or in the scene's `extras.recoil.loadRoot` for a load root:

| Property | Accepted value | Engine flag |
| --- | --- | --- |
| `altitudeSurface` | Boolean | `0x00000008` |
| `intersectSurface` | Boolean | `0x00000010` |
| `intersectBounds` | Boolean | `0x00000020` |
| `proximity` | Boolean | `0x00000040` |
| `landmark` | Boolean | `0x00000080` |
| `declient` | `"canModify"`, `"clipTo"`, or `null` | `0x00010000` or `0x00020000` |
| `overwrite` | Boolean | `0x00800000` |
| `altitudeZoneCheck` | Boolean | `0x01000000` |

Every omitted Boolean flag means `false`. Readers accept explicit `false`; writers emit only `true` flags. Boolean fields do not accept `null`. Missing or null `declient` means neither crater mode, and writers omit it; `"none"` and `"both"` are invalid. These source-format defaults do not inherit the engine's constructor defaults: reconstruction explicitly writes every enabled supported flag. Ordinary unmarked glTF uses the same false-by-default rule. For example, a standable, collidable surface eligible for craters carries `{"altitudeSurface":true,"intersectSurface":true,"declient":"canModify"}` within `extras.recoil`.

Earlier marked source formats, packed node `flags` and scene `rootFlags` are refused, even when the obsolete properties are null. Reconstruct the project from the original ZBD files; no compatibility reader or migration is provided for those forms. Bits 28–30 (`0x70000000`) have no source property and are normalized to zero in glTF-based source reconstruction and builds. This is an explicit source-format choice, not a claim that their historical purpose is known. Direct binary reading and saving retain their existing preservation rules. Material flags, mesh flags and Object3D `appearance.flags` remain separate attributes with their existing meanings.

Embedded node assignments use `"zone": "inherit"` when the parent's zone is effective, `"zone": "any"` for any zone, and numeric IDs 0–254 for a specific zone. A node without a zone assignment also inherits. Numeric object `zone: 255` and the obsolete `zoneInherited` and `inherit` fields are refused; there is no compatibility path for those forms. The altitude gate is the independent `altitudeZoneCheck` Boolean. A reference node can carry `zoneOverrides` with a structural `fingerprint`, ordered node assignments (`zone`, `altitudeZoneCheck`) and mesh objects containing `polygonZones` for that occurrence. The gate uses the same false-by-default, true-only output rule in an override assignment. Its `references` object holds deeper overrides keyed by the referenced file's node indices. The owning source path and the chain of reference occurrences select a placement; a repeated display name does not. Outer placement assignments take precedence over referenced-file defaults. Layout validation refuses stale assignments before a build or edit can attach them to another polygon.

Polygon ID order is retained. An empty array means no explicit IDs and differs from `[255]`, an explicit any-zone assignment. The engine's polygon count is derived from the array length; it is not a flag. Nonzero uninterpreted object padding is preserved separately as `zonePadding`, three numeric bytes in stored order. Noncanonical inactive polygon slots are retained as `zonePadding` on materials or sparse `polygonZonePadding` entries keyed by polygon index on primitives and override meshes. Malformed compiled polygon counts use explicit opaque `zoneRaw`/`polygonZoneRaw` byte records instead of pretending to be valid IDs. Ordinary assignments need none of these preservation fields. Packed hexadecimal `zoneWord`, material `zone` and packed polygon assignments are refused; reconstruct older projects from the original ZBD files. Readers and writers use the semantic representation described above.

Two settings make ordinary glTF viewers show the individual model geometry as the game draws it; builds read neither, and these settings do not provide linked-source Blender round-trip support:

- **Transparent textures.** The game takes transparency from the texture, not the material. A material whose PNG has alpha is marked **Alpha Blend** (`BLEND`), or **Alpha Clip** (`MASK` at 0.5) when its alpha is only 0 or 255, the texels the packs key out.
- **Pickup collision volumes.** A pickup's `bvol` node is its collision volume: the game registers an object as a pickup only when it has one, and switches it off at once, so it is never drawn (retail `Pickup::AssignBvolGroupAndId`, 0x41DB60). That is the one node named exactly `bvol` that `FindSubNodeByName` finds from the pickup (the file's roots from last to first, each node before its children, children from last to first), in a model a mission's build loads as a pickup (`LoadGameGen` under a template name `pu000`–`pu039`, or a placed pickup's `puNNNNN`, of the file the load finds through the model folders the scripts set); a node named `bvol` anywhere else is drawn. Its mesh gets a fully transparent material of its own (`~hidden`, Alpha Clip with base alpha 0) that keeps the engine colour and records its opacity (`opacity`, also in a material that had no engine attributes, which then also gets `normals`, so import reads it as before), so neither the look nor how an editor writes it back becomes the engine value. A material whose base colour is malformed is left alone. Keep the node: without it the model is no pickup. Tools that frame a model by its bounds still count the invisible volume.

Reconstruction replays each mission's scripts against its shipped world and undoes their edits (attaching, renaming, rearranging) in reverse, so each load's root holds exactly its file's scene. Files go where the original tree had them as far as the scripts show ([recoil-original-worktree.md](recoil-original-worktree.md)): a file whose script chose its folder (`SetModelDirectory`, as `bftN.gw`, `bftmulti.gw` and `weapons.gw` do) goes there, except that a vehicle several missions' vehicle scripts (`bft1.gw`–`bft6.gw`) load identically from their own folders is one file in `data\common\models`, which those loads also search (a differing version stays in its mission's `models\bft`, which its loads search first), and the effect models `weapons.gw` loads after setting `data\effects\models` are kept with their textures in `data\common\effects\models`, which the same loads search (the packs show the effect textures came from `data\common\effects\textures`, although `weapons.gw` sets `data\effects\textures` too); a file a script run by every mission loads identically (the pickups of `pickup.gw`) goes to `data\common\models`; a mission database and the files a mission's own scripts load go to that mission's `models` folder, one copy per mission; a load that finds an identical file in a folder searched earlier uses it. External references (models named inside other models) are written beside every file that references them, so two missions sharing one keep a copy each, as they keep their shared textures. The turrets are the exception (user decision): `pturret`, `nturret`, `samsite1`, `fturret`, `lturret`, `arcturt` and `sonictur` are one file in `data\common\models` that every reference names (such as `../../common/models/pturret.gltf`, keeping a second path's `./` spelling), when all their copies are the same file apart from their zones, reference no other file and find the same textures; each placement whose zones differ from that file keeps them as its zone overrides, so every mission builds the same world. A turret whose copies differ otherwise stays beside each file referencing it, with a reconstruction note. A copy never takes the name a load finds its own file by in a folder it searches first (it becomes `name_2.gltf`), so it cannot stand in for that file. Only folders that hold files are created: folders the scripts search but no shipped file comes from, such as `data\effects` and the multiplayer missions' `models\bft` and `textures\bft`, are left out (the build finds nothing in a missing folder either). Polygons keep their authored corners and UVs as the original build stored them (repeated corners, non-planar polygons and UVs are kept; only the tile shift and 1/256 quantization apply).

**Mission databases and their parts.** The shipped allocation evidence establishes that mission databases loaded several files, but does not recover every original filename or boundary: the database referenced files holding parts of the world (groups and objects) the way objects reference models, and the build copied each part in from a cache of it ([Engine evidence](engine-evidence.md#name-lookups-and-node-slot-order)). The order in which the build made and freed the nodes still shows in the shipped worlds' node slots, and reconstruction recovers from it:
- the database's records in their file order, with the groups the build deleted as placeholders (a reference to a part is named `groupN`; any other group takes the name still held by a freed slot no later node took, its own slot or, in an exact reading, the slot of its node in its part's cache, as m6's city part's cache keeps `street`, `ramps`, `bwall`, `phones` and `hydrants`; a group no such slot names is `groupN`; no slot names a group unless the database's deletion is the instruction right after its load, no other `DeleteTree` or `FreeNode` follows and no script the mission sources is missing), a group's last objects after it where its part's cache shows the group closed before them, and nodes in the order they were made (the world lists some levels of detail in another order);
- inferred loader sections with unrecoverable file names embedded in their owning glTF. A group's `extras.recoil.inlineSource` holds an opaque local cache `id` and a `count`: its first `count` children are the embedded section and its remaining children are the reference's own records. These marks retain cache/load ordering, including nested sections, without inventing physical `mN_NN.gltf` files or claiming that a cache ID was an original filename;
- references that named one file by different paths, which the build cached separately: the later paths are written `./name.gltf`, `././name.gltf` … (counted separately for each physical source file), and the build keys its caches by the reference as written (ignoring case, as Windows paths do), and the models it reads by the same key. The same holds inside model files: a model that named one file by two paths (`comanche.gltf` names `hturret.gltf` once as `./hturret.gltf`) is written so where a mission's slots show it, in that mission's database and the loads after it (in both releases every mission that loads it shows it); a load before the database, or another mission's file of the name, was built without it and keeps its own version;
- an unnamed node several records share (an OpenFlight instance definition) stays one node, written with the glTF profile's instance marks; the build makes it before the file's root. A cached file's identical unnamed subtrees, which its copies show expanded, are one such definition in its cache.

Since the slots alone cannot tell two loads of the same file under the same name apart, nor which of a model's references to one file took another path, reconstruction tries each reading. It then builds each mission database as the build will and keeps the reconstruction when every node takes its shipped slot or the closest parts model it finds, which is noted. The inline representation passes this slot check for every available mission of the original 1998 and 1999 releases; the corpus checks also verify shared-model identity and name lookups. Where the slots fit several of a file's references as the one that named it by its second path, the reference whose copy has models of its own is the one (copies of one cache share its models; m3, m5), and every later reference whose copy shares those models names the file by that path too. The build makes models as the original loader did: once per cache (a file named by another path, or read again by another file, has its own), each object its own, in the order the loader read them, so a rebuilt world shares each model among the same nodes as the shipped one. Where the records start on slots several earlier caches left free (m2), it searches for where the caches end in the free list: the boundary whose caches, simulated, end there and give back their high-water mark. Where the records start inside the copy of the first cache, which goes on into the fresh slots (m6), a world that kept that cache's slots free shows it whole at the bottom of its free list: reconstruction reads it from there and simulates the caches from it. Where no model fits, the database keeps its objects in the order of their shipped slots with a group at every slot the build freed, also noted: an object made later took a later slot, so of objects that share a name the shipped one is still made last and found first, and the later loads reuse the freed slots below the database as in the game.

Scripts name the project's files as written: `LoadGameGen` and the `dbName` macro name `.gltf` models and the texture commands (`CycleTextureSetMap`, `WriteTextureSetMap`, `LensFlareTexture`, `TextureAdd`) name `.png` images. Node names keep their spelling, also where they end in `.flt`.

Reconstruction validation compares the assembled world's nodes, placements, flags, grid cells, models and textures with the original mission; current validation results and remaining differences are recorded in [status](status.md). A mission's loads of the same file share its models, so it can have fewer model and material records than the shipped file.

**Models from other missions.** A mission can load any model in the project: add a `SetModelDirectory` for the other mission's folder and a `LoadGameGen` to a mission script, or load it into the mission's world with `zstudio_source_world_add_model` (MCP; the GUI's **Add model** is not available yet; [Mission worlds](#mission-worlds)). The load finds the first file of its name in the folders the mission searches, and a folder already listed keeps its place. The export then includes the model's geometry and materials in the world, and every texture it uses in the mission's packs, even when the texture lives in another mission's folder; the mission's own folders win for a name both have, as the engine finds the first match.

### Animations

Reading animation definitions and their keyframe scripts has a shared 64 MiB source budget and a two-million-node definition budget. Repeated definitions count toward those totals. Compilation also limits repeated wildcard expansion and cached syntax allocation to 64 Mi work units, reserving before creating indexed views or expanding another root. This can refuse excessive repeated syntax even when the resulting animation would be small. SI export keeps samples only over each track's authored frame span; it retains the existing compile-back verification and arithmetic.

`anim.zbd` is compiled from the mission's `data\mN\zrdr\anim.zad`, the definition files it lists (a path relative to the gamegen folder, or a bare name found beside the listing file or in `ANIMATION_PATH`; a missing file is skipped with a warning) and the keyframe scripts named by `OBJECT_MOTION_SI_SCRIPT`. Definitions bind to the world this export builds: a `NAME` listing several roots binds to the first the world has, a name with `*` (one digit each) expands to every matching node in name order, and a definition whose root the world lacks is left out, as the shipped files show. A node name the world cannot resolve, or an effect that the `effects.zrd` the game reads does not define (names match exactly), would make the game reject the whole file, so the export reports it. That file is the common one when a `zrdr` folder under `data\common` has one, since the game reads `effects.zrd` from the first archive that holds it; a mission's own `effects.zrd` counts only otherwise. Values that do not fit their stored field (such as an `EXECUTION_PRIORITY` above 255 or a `LOOP_COUNT` above 65535) and more than 32,767 entries, the most the game reads, are errors. The compiled file carries no source stamps, because the game rejects `anim.zbd` when a stamped source exists with a different time.

Every entry of every shipped `anim.zbd` recompiles from its sources to the same fields. A sequence named more than once takes its last `NAME`, as the shipped `deathmulti.zrd` and `sbarm.zrd` compiled; inside an event the first of a repeated attribute counts, as `machine.zrd` and `pipetrig.zrd` show. Five shipped definitions of 1999 (one of 1998) are not the versions the animations were compiled from. `anim.zbd` records the date of each definition file it read, and `zrdr.zbd` when it was packed: the m1 `frcgate`, `vwrebel` and `semideath` definitions anim.zbd read are dated 16 November 1998, and its `m13\zrdr\envmodels\bft_trans.zrd` 11 December, all after their archives were packed on 10 November (`bft_to_5cav` in that file moves the vehicle 55 units down, where the shipped animation moves it 47). Reconstruction rebuilds those from the compiled entries, so the project reproduces the animations the game shipped. Its note says so: the definition was rebuilt from `anim.zbd`, which the game uses and which was compiled from a newer version (with the date `anim.zbd` records), and what that version changes, for example `gen_vtol.zad: vtol_destruction* … (saved 4 Nov 1998) … Changes in the newer version: RESET_TIME ( 0.5 ) → ( 0 ); RESET_STATE › OBJECT_ACTIVE_STATE healthy › STATE ( ACTIVE ) → ( INACTIVE )`. Both versions are decompiled from what they compile to, so differences of spelling (attribute order, defaults written out, `1` or `1.0`) are not listed. Their archive members differ from the shipped ones, which the engine does not read at run time.

Effect-name discovery for animation builds shares limits across all outputs selected in one Check or export: 64 MiB of distinct effect-resource input, 64 MiB of estimated retained paths, names and cache entries, and 67,108,864 discovery and name-union work units. Each resource still has its 16 MiB limit. Successful per-file results are reused within that operation, while repeated unions spend work allowance and the final inventory and source-content checks remain required. This also applies when only animations are selected and no resource archive is built. Capacity or read failures refuse the affected build instead of supplying an incomplete set of effect names.

### Known differences

- Exported worlds give every node its shipped slot in every mission of both releases. Every lookup by name in the game finds the highest slot of the name first, so where names repeat and slots differ (in an edited world), an exported world can resolve a name to a different node. This affects:
  - animation roots: consecutive entries with the same root name take the following same-named nodes, then start again at the highest;
  - an animation's attachment (the node whose hits start it) outside its root, the node and tracked-node names inside animations that neither the attachment's nor the root's subtree has, and the first node of each activation prerequisite's path: all fall back to the whole world;
  - the `tex_fx` scripts' `FindNode`.

  Every name that repeats in a world (2,021 in 1999, 1,427 in 1998) binds to the shipped node in the exports ([Engine evidence](engine-evidence.md#name-lookups-and-node-slot-order)), and so does every lookup the game makes by name: every animation root and name, texture-effect `FindNode`, effect template and turret target.
- **Tools → Compare worlds…** checks an exported world against the shipped one, needing no open folder; either may also be a version-13 world of the July and August 1998 demos, and the summary names such a world's version. Choose both `gamez.zbd` files and **Compare**:
  - The tree merges the two worlds by parent-child structure: children match by name, repeated names first by their whole contents, then by their structure, their children's names and their nearest position, independently of serialized node slots. After pairing, child lists, world-cell lists and overflow lists are compared in encounter order because that order can change zone selection. Each row is marked `·` the same, `≠` changed (class, flags, zone, grid cell, transform, class data, model, child count or traversal order), `−` only in the shipped world or `+` only in the exported one, with the number of differing rows below it. A row lists at most 64 differences and counts the rest. Class data is compared without the pointers, slots and runtime counters it stores, and the nodes it names by name; a model by every value it keeps (mode, scrolling, morph factor, lens-flare entries without their runtime fields, bounds, and polygons with their corners' positions, UVs, normals and morph deltas and all their material fields).
  - A node under several parents appears under each, so the tree stops at 500,000 rows or 256 levels; the summary says so, and so does each row whose children it leaves out. The nodes it leaves out are still matched for `⚑`. The copies under one node are paired once however many places it has; copies too many to pair by position (more than 2,097,152 candidate pairs of a name, or 16,777,216 pairs examined in the comparison) are paired in order, and the summary says so.
  - `⚑` marks a node whose name several nodes share, where a whole-world lookup (highest slot first) finds it in the shipped world but another node in the exported one. Animations bind their roots and fall back to such lookups, but search their own subtrees first, so not every `⚑` changes behaviour. An indistinguishable copy (the same parents and contents all the way down, as the comparison sees them) counts as the same node; past 1,048,576 copy checks in a comparison, the summary counts the `⚑` it could no longer check.
  - **Differences only** hides rows with nothing differing below them; **Filter** keeps rows whose name, or a name below them, matches, and opens the rows that hold them. Selecting a row shows its slots, class, parents, children, flags, zone, grid cell, position and model in both worlds, with differing values highlighted. Stored slots and parent order are shown without counting as semantic differences; changes to child traversal order are reported.
  - Every world exported from a fresh reconstruction of either release has the shipped parent-child structure: no node is changed, missing or extra.
- Shipped name fields keep residue after the terminator; exported files have their own residue.
- `m9\gamez.zbd` names a texture, `surf00`, that no shipped pack holds; the game shows its default texture for it, and so does the exported world.
- Software packs choose direct colour by rule (damage masks and the horizon's textures), so they differ from the shipped ones where the developers chose by hand: the player vehicle's `tanktop` and `tankback` (m1: `tanktop`, `tankgn01`, `tankgn02`) and, in 1999 m10 and m11, `arcgun01`, `beamred`, `beamyelo` and `erfpgscl` are paletted, so the software renderer shades them and stamps no damage marks on the vehicle; m2's lightning sky `sky2lite` and 1999 m11's `m11sky` and m13's `skym6` are direct. Of the textures the shipped packs share, 38 records of 1999 and 14 of 1998 differ, all of these.

## Editing sources

For individual source-file inspection, open a plain folder above or within the project through MCP `zstudio_open_root` without `project` (the GUI opens only source projects); the project root itself opens the map picker. Text `.zrd` files then open in the shared ZRD viewer and editor (tree, Properties, `zrd_nodes`, `zrd_edit`) and save as text that changes only where the edit does: comments, spacing and the spelling of untouched values stay; new records are written in the canonical layout. A file the project's workspace holds unsaved edits of cannot be edited there until those are saved or undone, and the other way round. Importing a text `.zrd` into an archive compiles it. `.gs`/`.gw` scripts open read-only as token text; edit them in any text editor. WAV sources can be replaced with any 8- or 16-bit PCM file, PNG textures with any PNG, and glTF sources through the shared world editor or an editor that preserves the reference hierarchy and engine attributes. Use the bundled RECOIL extension for Blender round trips; ordinary glTF import/export does not preserve the linked graph and its provenance.

## Text formats

### zReader resources (`.zrd`) and animation definitions (`.zad`)

The original compiler's text syntax did not survive, and the retail engine only reads compiled data, so zStudio defines a lossless syntax, the same for resources and animation definitions. A file lists the children of its root array.

- `( … )` is an array. A key followed by its value array is written on one line: `GRAVITY ( -9.8 )`.
- Integers are decimal 32-bit values: `42`, `-7`.
- Floats always contain a decimal point or exponent (`2.0`, `-9.8`, `1E-45`). NaN payloads and infinities use raw bits: `f32:7FC00001`. Values round-trip bit-exactly, including `-0.0` and subnormals. The engine's `GetInt` rejects floats, so the distinction matters.
- Strings are bare when they start with a letter or `_` and contain only letters, digits, `_`, `.` and `-`; otherwise they are quoted with `\"`, `\\` and `\xNN` escapes. Files are written as ASCII and read as Latin-1.
- `#` starts a comment outside strings.

### Keyframe scripts (`.zan`)

The original scripts were Softimage "SI Animation Script" exports, compiled by a lost tool. Reconstruction writes them again in that format, and exports compile them as that tool did: the shipped keyframes of the 1998 and 1999 releases come back bit for bit (pad floats aside).

```
SI Animation Script
FRAMES: 521
OBJECTS: 1
Warning, file version 3.7 is later than DKit release version 3
Attempt to read: An error may occur...
Frame: 1
Object: copter01
Scaling:     1.000000 1.000000 1.000000
Rotation:    0.304886 -0.111792 -0.811317
Translation: 570.880615 48.131424 168.158310
Warning, file version 3.7 is later than DKit release version 3
Attempt to read: An error may occur...
Frame: 6
...
```

Each frame block gives every object's scaling, rotation (radians about X, Y and Z, applied Z, then Y, then X; values beyond ±π are allowed) and translation; a definition's `NAME` picks the object. `Frame: n` is frame n − 1 at the definition's `SCRIPT_FRAME_RATE`, and frames may go back (the engine plays reversed segments as authored). The header, blank lines, `#` comment lines and the Softimage DKit messages are not keys; a frame repeated immediately adds nothing.

The compiler turns consecutive frames into keyframe segments: a channel is kept in a segment when it changes (a position or scale component by more than 0.00001, a rotation by a half-angle above 0.00001 radians); the first and last segments keep every channel; a segment with no change is left out. Times are frame × the float of 1/rate; rotations go through the engine's own matrix, Euler and quaternion routines in single precision; rates are the change over the segment, with the spin taken from the engine's quaternion log and its fast square root.

Reconstruction writes the frames the compiler kept, with grid frames on the script's step where every object stood still. Keyed values are the six-decimal values the stored floats came from, and rotations the Euler angles that compile to the stored quaternions. A channel that stops before its next key ends at the value its stored rate reaches; between such points the compiler recorded nothing, and the held frames take the next key's value (as surviving fragments of the original texts show). Scripts of the shipped files also get the DKit messages their exporter wrote: before every frame (after every frame in the `m5doexit.zan` of 20 May 1998), with the Softimage version of the script's stamp date (3.5001 before July 1997, 3.7 until 4 May 1998, then 3.71). A script with no stamp date holds only its frames. The exit scripts list their objects as `vtol1`, `lengine`, `rengine`, `cargodoor`, as the fragments show. Keyframes that no SI script reproduces exactly (two poses at one frame, a first segment that does not move every channel, a value no six-decimal number reads back as, a rotation whose angles take too long to find, or a script larger than a project reads) are written in zStudio's keyframe format instead, with a note. A track whose keyframes are not on the frame grid of its `SCRIPT_FRAME_RATE` is not reconstructed at all, with a note. Translations and scalings of negative zero are written `-0.000000`, which reads back as negative zero. Rotation angles are never written as negative zero: keyframes only such an angle reproduces are written in zStudio's format, with a note (none of the shipped ones need it).

Fallback keyframe scripts allow 65,536 keys per object track and 262,144 keys across one file, within the 16 MiB source-text limit. Compilation shares an allowance of 1,048,576 retained fallback keys across its scripts, reserved before allocating each key. Reconstruction checks the writer's limits before appending tracks, then reparses and recompiles every fallback track to verify its meaningful keyframe values exactly. A fallback that cannot be represented is refused before reconstruction publishes the animation sources. These limits do not change SI compilation arithmetic. Both keyframe dialects read lines and tokens incrementally, observing cancellation during long scans. Each source is limited to 16 MiB and each significant token to 4,096 Latin-1 bytes; long comments and blank lines need no retained line arrays. Accepted object names remain complete, and writers enforce the same token limit before emission.

zStudio's keyframe format lists a track per object; exports compile both formats:

```
OBJECT copter01
FRAME 0 POSITION 1429.22 56.43 3107.5 VELOCITY 35.18 -8.75 -45.85 ROTATION 0.929 -0.128 -0.319 0.136 SPIN -0.003 0.130 0.020 SCALE 1 1 1 GROWTH 0 0 0
FRAME 5 POSITION 1440.95 53.52 3092.22 ROTATION 0.941 -0.121 -0.279 0.148
FRAME 2599
```

A key's channels start a segment that runs to the next key; the last key's frame ends the track. Frames count at the definition's `SCRIPT_FRAME_RATE` and may go back. POSITION and SCALE are XYZ, ROTATION a quaternion W X Y Z (not zero). A channel's rate may follow it: VELOCITY and GROWTH per second, SPIN as a rotation vector (half-angle radians per second). Without a rate, the channel moves steadily to its value at the next key that lists it, through any keys in between (their segments carry it on, since the engine holds a channel a segment does not key); with a rate, it moves only until the next key and then holds unless that key lists it. Two keys at the same frame are a cut, which jumps to the second value. A file without OBJECT lines is one track any node may use.

### Gamegen scripts (`.gs`, `.gw`)

Scripts use the engine's own tokenizer (`CZInterp::TokenizeLine`, retail 0x4C13C0): `#` ends a line, tokens are separated by comma, space, tab or newline, and ASCII whitespace after a separator is skipped. Only a separator directly after another produces an empty token, so zStudio writes empty tokens with commas (`a,,b`; a trailing empty token needs `a,,`). A script of more than 1,000,000 lines (as many as the instructions a build runs) or 4,000,000 tokens is refused before its lines are read; the retail scripts have at most a few hundred lines.

Opening and indexing source scripts forwards cancellation through tokenization and instruction-row construction. Replacing the workspace or cancelling the owning operation stops that work as well as preventing an obsolete result from appearing.

## Keep sources away from a retail install

Do not place a source tree inside a game folder. Loose `support\*.gw`/`*.gs` files override `interp.zbd`, and loose `*_easy`/`*_hard` resources change difficulty selection. (The shipped `anim.zbd` files are rejected when a source they stamp exists with a different time; exported ones carry no stamps.) Export into the game folder (or a separate folder) instead.

Prepared-script export limits the sources together to 64 MiB, one million instructions and four million tokens, in addition to each script's existing limits. Reconstruction rechecks destination parents before creating or rewriting a source, so a directory replaced by a link during reconstruction is refused.
World builds cache at most 64 MiB of script source and four million decoded tokens across distinct sourced files; repeated sourcing reuses that parse. Exported worlds, compiled animation packages and the project paths the export looks up (each distinct path, absent ones included, is kept to check before publication, about 160 bytes plus its text) share a 1.5 GiB retained-data estimate across missions. An export exceeding it is refused before retaining the next result; select fewer missions per export. Animation preview reads effect resources directly from decoded zReader records, without making full inspection JSON, and supports up to 4,096 effect templates and 65,536 texture-map references in one preview.

Terrain Properties creates at most 32 region rows at once; Previous/Next reaches every region without expanding all region summaries. Model imports refuse vertex colours that RECOIL cannot store; bake them into the texture first.
Altitude comparison bounds its spatial index to one million entries and its comparison work to 200 million candidate/node/polygon-corner units. If either is exceeded, the GUI and MCP report an unavailable comparison; the accepted conversion remains undoable. Extreme finite UVs or morph positions that overflow their derived stored values are refused before adding polygon data.
Model imports refuse glTF skinning and animation channels rather than silently making them static: bake an armature's intended pose into the mesh, and author runtime animation in the project's .zad/.zan sources. Inferred database groups obey the source glTF depth limit; an inference beyond it uses the existing noted fallback instead of recursively constructing an unrepresentable source.

Reconstruction limits additional retained world output to 512 MiB and animation tracks/text/output to another 512 MiB; animation scripts use at most four concurrent writers. Inference charges all replayed node allocations, including attempts that create no caches. Terrain compilation charges created corners before intermediate splitting and junction repair. A region's outline is indexed only over the surfaces it applies to, so erasing strokes from a region that covers its whole surfaces (everywhere but the strokes) costs about what painting them does. Each part is cut by the outline edges whose segments cross it, in outline order, each passing only to the pieces it can still reach; a part carrying more than 64 edges is first halved across them along x or z. Whether a piece lies inside is found from its bucket of the outline index: the rings odd at the bucket's centre (one ray per row, cast once), toggled by the bucket's edges between the centre and the piece. Junction repair finds each edge's points by parameter. On a 64 × 64-quad heightfield (8,192 triangles) and a 128 × 128 one, 500 radius-8 drags (88,000 outline points) paint or erase in about 16 million of the 100 million work steps, to about 122,000 and 145,000 polygons. SI script writing indexes frame occurrences and schedules active tracks, preserving reversed frames, gaps and original object order without scanning every track at every frame.

Reconstructed model placement separately admits transitive reference copies before retaining them. One reconstruction shares 64 Mi units each for placement metadata and path work, including full paths, queued copies, reference adjacency and sorting. These are conservative accounting allowances, not measurements of heap usage. A shared reference used from many source folders consumes capacity for each required copy; exceeding either allowance refuses reconstruction instead of returning an incomplete reference graph. Complete path identities, deterministic placement order and the first applicable texture-search context are preserved.

Keyframe compilation shares a 16 Mi-unit work allowance across every script, event, root and sequence in one compilation. It counts track indexing, authored pose visits, segment checks and fallback lookahead before doing the work, including stationary or empty-channel keys that produce no intermediate output. Parsed-script reuse does not reset the allowance. Reaching it refuses compilation; reduce repeated motion events or simplify the tracks. The original SI arithmetic and exact compile-back checks remain unchanged.

Animation-definition repair shares a syntax-node and retained-memory allowance across the reconstruction, checked before decompilation, generalization and replacement copies. Exceeding it refuses reconstruction; it is not treated as an unsupported definition that can be silently skipped. Candidate text remains limited to 16 MiB and is used only after it compiles back to the shipped animation meaning. Count-mismatch diagnostics report the event counts without expanding every event type into a message.

ZRD writers charge escaped string length before creating escaped copies, and scalar replacements share an output budget. Text and animation diagnostics show bounded previews of authored values. Animation compilation refuses nonfinite operands and finite inputs whose derived ranges or rates overflow a game float.

Terrain Properties loads recipes off the UI thread and ignores results superseded by closing, retargeting or a source revision change. Region navigation and brush settings reuse the loaded recipe; rows show outline-part and point counts. Duplicate-surface checks and brush construction run with the background source edit.

Direct compiled-file saves retain atomic replacement. Their external-change check is immediately before replacement, but another program can still change the destination between those operations and have that change overwritten. This concurrency race remains unresolved by explicit user choice; the source project's recoverable publisher uses a different protocol that holds and moves the expected originals.

Terrain shape clipping checks complexity before polygon intersection/offset expansion: at most 200,000 weighted input edges and one million potential edge pairs (boxes overlapping along both axes). The pairs are counted by a sweep along x that holds the boxes it has passed and counts those overlapping each new box along z from prefix sums over their extents, so the check costs about n log n for any shape; a shape spread along x, such as hundreds of separate strokes, is not refused for the sweep's own work. A brush stroke within a conservative reservation of 64 edges per segment is offset as one path. A longer stroke, such as an ordinary viewport drag sampled every quarter radius, first drops the points within 1/64 of the radius of the line kept around them (measured to segments, so a reversal is never cut short; the painted edge moves at most that far, beside the arc tolerance of 1/64 radius). Pairs of its remaining segments within reach of each other are checked before any offsetting; it is then offset in pieces of 16 points and the pieces are united after their actual edges are checked. Complex shapes and dense scribbles or crossings can be refused with simplification guidance; the checks are shared by GUI and MCP. Regressions include dense crossings, an ordinary 20,000-point circle, long drags with a reversal, painting, holes and islands.

### Import refusals and edit preparation

A glTF primitive must be triangles, a triangle strip or a triangle fan and have a POSITION attribute. Points and lines are refused; they are never silently omitted. Every decoded accessor component, including sparse replacements, must be finite. Source-script numbers must fit a finite float, and derived camera/light values, transforms, geometry and bounds must remain finite when compiled and written. A failed build publishes no outputs.

An untextured MASK material becomes either fully transparent or fully opaque according to its `alphaCutoff` (default 0.5). The game takes a textured surface's transparency from its texture, keying out the texels below alpha 128 of a PNG whose alpha is only 0 or 255 and blending any other alpha, so a textured MASK material is built only at the 0.5 cutoff where it records the engine's material: its texture name (reconstructed keyed-texture presentation), or with base alpha 0 the opacity of a hidden collision volume. Other textured MASK materials are refused; bake the mask into such a PNG and use BLEND. Nondefault cutoffs are retained when writing glTF, so preflight can refuse unsupported semantics rather than erase them.

Terrain marker creation accepts at most 16 MiB of JSON per database/reference file, before reading it into memory or constructing a JSON tree. Terrain placement and name lookup index each immutable source document once per load, retaining name ambiguity, transforms, inherited zones and appearance, and carried flags. All terrain source documents and recipes in that load share 1,000,000 node-visit/name-lookup units and 32 MiB of name/attribute text work, charged before decoding, normalization or index growth. Creation and candidate mesh listing use the same bounded, cancellable traversal. Move inline buffers into separate files or simplify metadata when this limit is reached. The marker is serialized directly as compact UTF-8. Terrain recipe reads enforce their 64 MiB limit before loading the file. Terrain, model additions, object edits and placement edits prepare against an isolated source workspace on a worker thread. Acceptance checks workspace revision, read-file stamps and other editors before publishing one transaction on the UI thread; cancellation or a conflict leaves history unchanged. Scene-card drafts remain until preparation succeeds and that exact draft is still current.

Terrain creation follows up to 50,000 distinct model-file references, including references through `gamegen/` and binary glTF (`.glb`) intermediates. The complete walk shares a 512 MiB input allowance, intersected with the 16 MiB whole-file limit before each read or prepared-content hash. The allowance counts complete GLB payloads even though the walk inspects their JSON. If the complete traversal needs more files or bytes, it refuses before creating a recipe or marker. Duplicate edges and already visited cycles do not consume extra capacity; an exhausted traversal cannot return a partial set of protected models. Cross-mission transform checks use the same glTF/GLB container reader as the importer, so a binary intermediate cannot hide another mission's use of the edited model.

Terrain creation also prepares its recipe inventory and bounded completion pages on that worker, before accepting the edit. The returned list combines that inventory snapshot with the created recipe. Completion does not rescan the project after publication; a later cancellation cannot report an already accepted creation as canceled. Unrelated recipes in the inventory are observations, not additional edit dependencies.

Model import tracks child links by object identity while retaining authored order. Duplicate link attempts and ancestor checks share the build's cancellable work allowance. Source reparenting prepares a bounded hierarchy index once per immutable editing phase, preserving first-parent semantics and inherited zones. It prepares replacement links and transforms before mutation and rebuilds the index for checks that inspect the resulting hierarchy. An exhausted allowance or cancellation before acceptance leaves the source transaction and history unchanged.

Reconstruction reserves input and conservative decoding space before opening the next world, texture pack, animation package or archive directory, then accounts for the retained representation. It may refuse a large custom dataset even when each file individually fits. Within a sound bank, repeated names are allowed only for byte-identical WAV payloads, as found in the retail banks. Differing same-bank duplicates are refused; best-quality selection is only across banks.

The profile menu enumerates files on a worker. Shared profile selection is cancellable through Tools/Cancel or the MCP operation; a canceled scan leaves the choice unchanged, and a scan from an earlier workspace or selection cannot replace the current menu.

All model input paths used by builds and previews must remain under `data/` or `gamegen/`. Script model/texture search directories outside those source roots are ignored, and model/buffer/texture references into `.zstudio/` or other non-source folders are refused.

The shared glTF reader bounds the complete JSON before constructing its DOM: 32 MiB, four million tokens and nesting depth 64, including unknown properties and inline data. Large binary payloads should use external `.bin` files or a GLB BIN chunk. The existing aggregate buffer and decoded geometry limits still apply. Source node editors use the same JSON guard. Authored normal, occlusion, emissive and metallic/roughness texture channels are refused; explicit metallic and roughness factors must be 0 and 1 respectively, and explicit emissive factors must be zero. Bake unsupported appearance into the base-colour texture before importing. KHR texture transforms apply scale, positive counter-clockwise UV rotation, then offset.

Project file providers receive the caller's size and remaining input allowances before allocating the payload. Text scripts and animation sources retain their 16 MiB per-file limit; compiled resources retain their separate binary allowance. Resource classification and glTF JSON/GLB header checks use the same held file handle as the read. Model buffer resolvers receive the remaining allowance before reading each external file and account for actual bytes, including trailing data, rather than trusting its declared length. Pending source arrays pass the same admission before hashing, copying or decoding. The narrower 16 MiB terrain database policy remains in effect. Terrain reference inspection shares a 512 MiB input allowance across distinct resources, keyframe files and scripts, including files containing only comments or repeated names; the scripts also retain their separate 64 MiB aggregate allowance.

Workspace presence checks use file metadata and accepted pending additions or removals, without reading or hashing the payload. Prepared edits record presence dependencies separately from content dependencies: adding or removing a required file invalidates preparation, while a content-dependent read still requires its verified digest. Source-world opening and terrain-recipe discovery use these same presence checks.

Terrain conversion also accepts a database with implicit roots and no scenes: its edit writes an explicit scene with the same roots and order before replacing converted pieces with the terrain marker. Conversion database JSON has the same 16 MiB pre-read bound as Create terrain.

Material import applies glTF defaults: metallicFactor defaults to 1, including an unassigned material, and must be explicitly 0 for RECOIL. Base-color components must each be between 0 and 1. PNG palettes are forbidden for greyscale types 0/4, and indexed palettes may not exceed the bit-depth capacity. Export warnings compare existing texture packs with the outputs selected for that run, including unselected packs from the same profile.

Terrain recipe serialization writes coordinates directly to bounded UTF-8 output and refuses recipes exceeding 64 MiB before creating an oversized result. Read-only inspection can still show a region whose area cannot be calculated within the editing complexity limit; MCP reports a missing area with its reason, while preserving counts, bounds and bounded coordinates. This does not change painting limits.

Original-data reconstruction decodes the unique `anim.zrd` member and requires top-level animation definitions; a misleading filename, malformed payload or duplicate member does not qualify a folder as original data.

Terrain conversion plans projected triangles directly, without rounding them onto a clipping grid or discarding a small positive overlap. Edge-only contact is not an overlap; overlapping sheets stay in separate surfaces. Planning caches each mesh projection and refuses work beyond 200,000 triangles or eight million geometry visits/comparisons, checking cancellation throughout. Wildcard-reference matching has a separate 16-million character-work budget. These limits apply to GUI and MCP planning before any conversion is applied.

Source workspace baselines and prepared-edit dependencies retain content digests. Reuse, external-change detection, reload and acceptance compare content through a held read handle, including when length and modification time are unchanged. Animation compilation and reconstruction index world names once, preserve numeric wildcard ordering and share a 16-million character-work budget across definitions, with cancellation checks during matching. Sound format declarations, recorded image paths and animation source-list updates traverse the full parser-accepted tree depth; accepted nested data is not silently skipped at depth 64.

Prepared source edits verify content off-thread and hold existing dependencies read-only until acceptance; more than 4,096 dependencies refuse before handles are opened. Owning workspace/fork revisions and absent paths are checked again at acceptance. Source reload content checks also run off-thread and reject a changed workspace before clearing history.

World comparison preserves texture-directory multiplicity and checks stored load states and next-variant links. Distinct names may reorder; duplicate names pair by their directory occurrence, so an ambiguous reordered duplicate is reported conservatively. These differences appear on the world row in Compare worlds and MCP inspection, with full counts and bounded detail text.

Reconstruction probes and hashes each input through the same read-only handle, then verifies its digest on every subsequent read, including the original-data check. Its initial consistency pass refuses more than 4 GiB of input bytes before hashing. A same-length, same-timestamp replacement therefore cannot enter the reconstructed project. glTF imports require canonical supported `asset.version: "2.0"` (and a canonical `minVersion` no greater than `2.0` when supplied); material `flags` and `packedColor` must fit their unsigned 16-bit stored fields and are checked before import mutations.

An out-of-directory texture-variant index is refused by the shared world reconstruction/comparison reader rather than silently becoming no link; original document bytes remain inspectable. Valid directory cycles retain their stored links and compare without recursively expanding them.

Source validation rejects missing or empty glTF mesh primitives, non-array collection and extension declarations, and matrices whose homogeneous terms are not [0, 0, 0, 1]; these cannot silently become an empty model or a different transform. Point-only engine records use the current node `extras.recoil.model` representation; obsolete empty-mesh representations are refused. World partitions must advance along +X and -Z and produce positive cell counts before changing the grid, and stored negative or single-zero grid dimensions are refused by both GameZ readers and the writer. All world nodes in one GameZ document share the 65,536-cell budget, checked before metadata or output allocation. External-change checks for a displayed source world inspect that build's dependencies and resource archive membership; workspace-wide Save checks the dirty files it will write, while Reload checks every touched file against its baseline.

Checks and exports refuse an animation file when a compiled entry needs a missing attachment, tracked node, node reference or effect template. The first known engine rejection is retained independently of the warning cap, and a failed export publishes nothing. Shared definitions whose root is absent from the mission are still omitted; references cannot be checked when their world script or effects resources are absent. Software texture packs keep the texture named by the final expanded `WriteTextureSetMap` argument unpaletted. Discovery executes each mission's build and runtime load scripts through the shared script service, with independent macro state for the two entry points. It follows executed includes and conditions and includes registrations after the world write; unused scripts and skipped branches do not register masks. Parsed sources and execution allowances are shared across the export, while completed mask sets are cached per mission. A read or capacity failure refuses discovery without supplying a partial set. A glTF buffer must declare a positive `byteLength`; missing, null and zero lengths are refused before external buffers are read. Bufferless models remain supported.

An effective glTF engine node name must fit 35 Latin-1 characters without NUL. A recorded engine name takes precedence over the editor display name, and the usual Blender `.001` suffix is removed only when no recorded name exists. Present `extras.recoil` values must be objects; material `fields` and `color` must each contain exactly three finite numbers. Invalid values are refused before importing source state. During reconstruction, same-named scripts with different instructions refuse the operation instead of mixing versions; identical duplicates share the first source. Image placement checks eligible names without allocating normalized copies of unrelated resource strings and ignores recorded image paths longer than 4,096 characters.

World comparison includes the primary root's stored name and material texture references by case-insensitive directory name plus occurrence, matching texture-link comparison; repeated names remain separate identities. Source builds apply CameraSetHorizonXZ alongside CameraSetHorizon, resolve both to Object3D nodes, retain command/reference provenance and clear bindings to deleted nodes. CameraTranslate, CameraRotate, CameraSetActive and the individual CameraSetNearClip/CameraSetFarClip commands remain unimplemented by source builds and now produce explicit warnings instead of silently disappearing; the combined CameraSetNearFarClip remains supported. Automatic texture-pack planning reads each PNG's current 24-byte header on every plan, including the publication replan, so unchanged timestamps and lengths cannot retain stale dimensions.

Source planning shares each mission's model and keyframe inventory and refuses plans exceeding 1,000,000 input references across all outputs before expanding them. Pending source files obey the same 50,000-file inventory limit as disk files. These limits apply to GUI listing/builds and MCP status/export, before paging results.

A glTF with multiple scenes must name its default through the top-level `scene` index; an absent or null selection is refused before buffers are read. A single scene without that field remains supported. GameZ reconstruction and comparison refuse invalid textured-material texture indices, polygon material indices and live-node model indices instead of treating them as absent; the valid optional material/model sentinel remains -1. Raw document inspection remains available.

Source builds report every recognized but unimplemented world command, including Object3D activation/priority, LOD construction, materials and model construction. A small explicit set of diagnostic and renderer/runtime-global commands has no saved-world effect and is ignored. Warnings appear in Problems and source-export reports; a warning does not mean the command was implemented.

## Building worlds

A mission world is built by running its build script with the retail interpreter's command semantics (`WorldAssembler`). `SetModelDirectory`, `SetTextureDirectory` and `RdrSetPath` keep the engine's search-path lists (`RdrSetPath` empties the zReader list first, `zRdrSetPath` 0x48cca0): `zRdrAddSearchPaths` (retail 0x4a5ce0, which `SetTextureDirectory` reaches through `zImageInitMissionResources` 0x46ebd0) adds each `;`-separated folder at the head of the list only when the folder exists and the list holds no entry with exactly the same text (`strcmp`); a listed folder never moves. The gamegen tool's own `SetModelDirectory` is lost; it is taken to use the same zUtil routine. So `weapons.gw` and `bftN.gw`, which name folders `common.gw` has already listed, leave the order as it was: in the original build tree m1 searches its models in `data\m1\models\bft`, `data\common\effects\models`, `data\common\models`, `data\effects\models` and `data\m1\models`, and its textures in `data\common\effects\textures`, `data\common\textures`, `data\effects\textures`, `data\m1\textures\bft` and `data\m1\textures`, for the whole build.

Folders compare by their text as written, as `strcmp` does: another spelling of a listed folder (case, separators) is a new entry at the head, and since Windows finds the folder under any spelling, that folder is searched from there. A folder is listed only when it exists in the project; one that does not (such as `data\effects` in a reconstructed project) would hold nothing to find either.

Finding and reading inputs share one allowance per world build: 131,072 existence probes (each model candidate a `LoadGameGen` tries, each texture folder a textured material tries, each folder a directory command tests, and each script, model and referenced file looked up) and 1 GiB of model, buffer and terrain bytes read (a load reads its files again, declared but unused buffers included). The retail missions make at most 4,710 probes and read at most 12.3 MB (1999 m6). A build past either is refused before the next probe or read, with what to reduce.

Commands that change nodes store what the engine's setters store. `Object3DTranslate` sets a node's translation and keeps a matrix its glTF node authored; `Object3DRotate` and `Object3DScale` replace that matrix with one built from the rotation and scale the node stores (0 and 1 until a script sets them) and its translation (`gwObject3DSetPosition` 0x44e300, `gwObject3DSetRotation` 0x44e030, `gwObject3DSetScale` 0x44df00), with angles converted as the interpreter converts them. `LightNew` makes a white point source at full intensity with ranges 32 and 64 (`gwLightNew` 0x452fd0); `LightSetColor` clamps each channel to 0–1, equal `LightSetRanges` become 10 apart, `LightSetDirectional` sets only the directional flag, and `LightSetActive` sets the active flag of the camera, world, object, level of detail or light it applies to (`gwNodeSetActive` 0x447c60). `CameraSetHorizon` and `CameraSetHorizonXZ` find a node of any kind, and `CameraSetWorld` keeps the camera's world when no world has the name. A texture a script registers is named as the engine names it, by its file name up to the first dot (`TexDirSetBaseNameFromPath` 0x46e380); the texture-effect scripts' textures, which the game registers itself as the mission loads, must be named without a folder and in at most 19 characters, or the game cannot find them, and the build refuses them.

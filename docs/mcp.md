# MCP access to the visible workspace

MechWarrior 3 base-game support adds mission selection, motion inspection/editing/playback and member-local mech mesh replacement. See [MW3 workflows and MCP commands](mechwarrior3.md). `event_catalog.version` selects 28 or 39; `resource_properties` supports motion part/frame targets and generated actions. Every operation uses the shared visible workspace and existing document revision, draft, undo and save guards. The embedded discovery catalog contains 89 tools.

Ordinary animation opening and inspection use bounded summaries for both versions 28 and 39. Entry inspection includes four records per reference table, four puffer records and sixteen sequence summaries, with full counts and truncation flags. Sequence Properties includes eight event previews. Events retain their decoded scalar fields and at most 256 raw bytes (`raw_hex_truncated`); sequence tails use the same byte limit with an explicit full size. Keyframe streams are omitted from passive JSON (`keyframes_omitted`); inspect/edit a particular segment through Properties or `property_fields.segment`. `animation_records` pages event identities and these bounded fields, applying queries before pagination. `references` pages reference slots. Explicit JSON export retains complete payloads, references, sequences, tails and keyframes.

`inspect_asset` limits model geometry to 32 vertices/normals/morphs/polygons, world lists to 32 nodes/materials and sound cues to 32, with original counts and truncation flags. Authored nested metadata is copied with a shared budget of 512 JSON nodes, twelve nesting levels and 8192 text characters (1024 per string); `properties_truncated` discloses omissions. Nested polygon/node/material rows and `scene_nodes` use 64 JSON nodes and 1024 text characters per metadata row so maximum pages and paired snapshots remain usable; `scene_properties`, scene selection and GUI source inspection use the larger budget and `inspection_truncated`. JSON exports retain full data. These limits apply before copying or serializing large authored values.

`motion_records` track names use 512-character previews with `nameCharacters`/`nameTruncated`; queries still match the complete stored name. Frames, record identities and explicit JSON exports remain complete. Retrying an in-flight MW3 mission selection waits for a displayed result; superseded selection operations return `context_changed` and cannot persist stale preferences.

MW3 scene actor labels and `scene_nodes` name queries use at most 128 characters. The actor exposes `NameCharacters`/`NameTruncated`; node metadata also records `name_characters`/`name_truncated`, subject to the metadata budget. Object cards disclose shortened names. Source AIV names remain complete for matching and export; archive/member/record identity distinguishes identical label prefixes.

Inspection-panel resizing shares `workspace_view.changes.inspectionPanelHeight` (DIP, default 432, minimum preference 216). `scene_inspect.panel` returns preferred/effective heights, viewport-dependent limits and expanded state. The expanded panel is capped at 80% of the viewport; automatic clamping preserves the preference and pending drafts. The GUI bottom grip and keyboard resizing use this same layout state. Rotate stays hidden for placements without authored rotation.

The fixed top-right inspection panel and shared transform drafts use `scene_inspect`, `scene_card`, and `drafts` / `resolve_drafts` with `target: "scene"`. Whole world card and AI marker selection require `pickup_lock` to be unlocked; source/tree inspection and read-only queries remain available while locked. A 1998 demo world (GameZ version 13) opens read-only: its Unlock editing button is disabled, `pickup_lock` refuses to unlock it with `read_only`, and its placements can be inspected but not edited or saved. The permanent hover readout stays independent of selection; scene_card select expands details downward and clear collapses only those details. Selection shows bounds; Edit reveals the reserved Move/Rotate controls, enables handles and makes persistent authored fields editable. `scene_card set` accepts position strings, pickup `rotationDegrees` XYZ strings, vehicle `headingDegrees`, and `transformMode`. AI nodes support translation only. These inputs and GUI drags preview without accepting edits; apply creates one combined undo step and cancel restores the accepted transform. Native angle units and untouched bytes survive position-only edits. Copy retains accepted values and labels. See [3D inspection and transform editing](scene-inspection.md). The generated discovery catalog contains 102 tools. `scene_tree` exposes the shared Document scene hierarchy, context-scoped rows, bounded root/child pages, expansion, collapse, reveal, guarded selection and pinned Properties. Animation trees show the stable bound scene; cards retain exact runtime identity.

Native model round trips use `model_bundle_export` and `model_replace`, with explicit source fingerprints/model indices, shared document undo and frozen preview snapshots. `save_document.modelDirectory` requests verified model/texture Save As; ordinary save stages all variants and commits textures before GameZ. `inspect_asset` distinguishes original and edited GameZ content. Motion metadata caps part/name previews with totals and truncation markers; `motion_records` pages complete tracks. `mech_models` caps nested node/material previews and pages full references through `section` and `localModel`. See [MW3 inspection paging](mechwarrior3.md#mcp) and [the model replacement workflow and limits](model-replacement.md).

Responsive Files uses the existing `workspace_view` service. `changes.filesWidth` sets its preferred separate-column width (default 240 DIP, clamped to 200–650); `navigatorWidth` remains the other tabs' width in split mode and the combined tab group's width in compact mode. The response includes effective `navigatorMode`: `hidden`, `tabbed` or `split`. `navigatorTab` keeps stable identities 0 Files, 1 Assets, 2 Search and 3 Document scene, including when the Files tab header is hidden because its tree is already visible separately. Unavailable document sections fail before any preference changes. `layout.BrowserTab` is the active logical section; `layout.ContentBrowserTab` remembers the non-Files tab separately. Automatic layout/fallback does not overwrite those preferences or dimensions, commit drafts, navigate source records or recreate previews. Navigator visibility/presets govern both columns. No new access toggle or discovery-time window is introduced.

zStudio exposes its current capabilities to local AI agents through Model Context Protocol. GUI and MCP use the same documents, accepted edits, undo history, preview player, renderers and verified save/export paths. This is a local shared desktop workspace; it is not a headless converter or a remote HTTP service.

## Connect

1. Run the MCP-enabled build of zStudio and open **Tools → MCP integration…**. This menu is available on the welcome screen.
2. Check **Enable local MCP access**. The choice persists and is off by default.
3. Use **Copy configuration** to obtain the exact executable path for your installation. Add it to your agent's MCP configuration using its supported configuration format. The standard JSON form is:

```json
{
  "mcpServers": {
    "zStudio": {
      "command": "D:\\Tools\\zStudio\\zStudio.exe",
      "args": ["--mcp"]
    }
  }
}
```

The connector starts quietly in the background. Initialization, ping, tool/resource discovery and capability-schema inspection do not open or connect to a GUI. The first valid workspace tool call (including `zstudio_state`) or read of `zstudio://state` attaches to a running instance of that installation. If none is running, it asks the Windows desktop shell to launch a visible workspace. Concurrent first requests share one connection/startup. MCP access is checked at use time, so disabling it after agent startup still prevents access. Disabled access permits static discovery only. Disconnecting a client leaves the workspace open, including unsaved edits. Accepted application closing cancels retained preview/editor lifetimes before waiting for MCP teardown, preventing preview recovery from extending shutdown. Canceling a close leaves those lifetimes active; disabling MCP alone still recovers the retained preview. Concurrent stop requests share teardown, and access cannot be re-enabled during teardown or accepted application shutdown. The connector writes only MCP traffic to stdout; startup errors go to stderr. If several instances of the same installation are open, the connector refuses to choose silently. Copy the desired instance ID from the integration window and use `"args": ["--mcp", "--instance", "ID"]`. Instance IDs last for that process lifetime.

The integration window shows connected-client count on Refresh, instance identity and the latest 200 activity messages. **Disconnect clients** drops current workspace connections. Reconnect the MCP client afterward; a disconnected connector does not silently reopen the workspace or replay a request. Unchecking **Enable local MCP access** stops the listener and resolves in-flight automation shutdown; recheck it before reconnecting. It does not provide an agent-callable command to enable access. Local processes running as your Windows user can connect while enabled, so connect agents you trust with the open workspace.

## Discover and operate

Start with `zstudio_state` and `zstudio_capabilities`. Standard `tools/list` exposes typed input schemas; `resources/list` exposes `zstudio://state` and `zstudio://capabilities`. Tool results include text JSON and structured content. Capture additionally returns an MCP PNG image block. Array schemas include element types and constraints: camera `position` and `look` each contain exactly three numbers, and optional rotate/zoom `screenPoint` contains exactly two viewport DIP coordinates; export `assets` contains objects with a valid `kind` and integer `index`, both required, with no extra fields. Recursive validation rejects malformed arrays with `invalid_argument` before executing a handler or launching/attaching the workspace. Pickup `source` identities require the exact `ArchivePath`, `AssetIndex`, `ResourceName` and `RecordIndex` fields. Save As destination maps accept only string paths. File and folder arguments are full paths (`open_root`, `open_document`, the Save As `destination`, `destinations` and `modelDirectory`, export destinations, and input files such as those of `texture_import`, `archive_edit`, `mech_model_replace` and `model_replace`): a relative one would resolve against zStudio's own folder, which a new build replaces, so it is refused with `invalid_argument` before anything is read or written. Project paths of the source tools (`model`, `recipe`, `file`) and the Blender `export` path stay relative to the project or the checkout's outbox. Integer schemas enforce handler bounds; source byte offsets and revision IDs retain nonnegative 64-bit ranges.

Long-running tools return an operation object with `id`, `Name`, `State`, `Cancellable`, and `result`. The initial state may already be completed. Poll `zstudio_operation` using the ID until `completed`, `failed`, or `canceled`; inspect the nested result. Operations continue after a client disconnects. Exports, validation, source project and source world operations (including resolving an interrupted save) and world comparisons accept manual cancellation; workspace replacement and application shutdown still cancel obsolete work automatically. At most 128 operation records are retained, including queued work. Read-only workspace/status tools remain available while an operation awaits background work.

Use document lifetime UUIDs, asset kind/index, sequence/event UUIDs, and complete pickup source identities returned by discovery. Names are labels and are not unique. Each accepted edit increments the document revision. Mutation tools require the expected revision; a stale request returns `revision_conflict`. Preview commands require the current preview lifetime UUID. Re-read state after navigation or changes that replace a static preview. GUI actions can supersede agent work; context changes are reported rather than redirected to a different document.

`zstudio_drafts` reports pending Properties or preview input and a conflict token. Resolve it explicitly with `zstudio_resolve_drafts`, the owning document, current token and `apply` or `discard`. Invalid values remain visible. Accepted edits are separate from drafts: `close_document` requires `discard=true` to abandon unsaved edits. There are no file-picker or save-confirmation dialogs in the MCP workflow. Resolving animation settings applies a frozen approved Seed/Height/Range batch; newer input is retained and reported as `draft_conflict`. A replaced draft owner cannot return success. Mutation calls return `busy` while a shared GUI/MCP save or a GUI modal dialog is active; read-only state and operation polling remain available.

`properties_open` succeeds only after the requested target is published, and returns its document and asset identity. Superseded/closed targets report `context_changed`; input entered while properties are decoding reports `pending_drafts` without retargeting or showing a modal dialog. Decoding and queued dispatcher work observe request cancellation, including non-job calls. Large JSON/keyframe/WAVE expansions check cancellation during traversal. Inspection links request/document lifetime, freezes edited animation data at one revision and rejects closed (`stale_document`) or changed (`revision_conflict`) documents before returning. Original animation data is separate from the working edit collection, including across Undo/Redo. Reload parses and validates a replacement before swapping it into the workspace: malformed, inaccessible, canceled or superseded staging retains the existing document and preview. New edits/drafts reject publication. Successful parsed-document publication is the commit boundary; subsequent content preview preparation follows normal loading/recovery behavior. Background reloads do not change the active document. Window close is deferred until its response can be sent; new edits, drafts or an active pickup drag cancel that pending close without prompting or committing input.

Folder/file opening revalidates navigation ownership and unfinished input after asynchronous preflight or parsing. A newer GUI navigation supersedes an older request, including when the newer file is still loading. MCP root replacement never opens a late save/discard prompt. Late pickup-load, export-progress and validation results cannot publish into a closed document or replacement workspace. GUI file browsing retains a pinned Properties window and its drafts.

## Capabilities

All tools below have the `zstudio_` prefix. Call `capabilities` for current schemas and option names.

`archive_edit` and resource `undo_redo` reconcile the visible preview with the resulting selection, including while Assets is hidden. Removing the active motion or replacing it with another content kind disposes its viewer; a surviving motion retains transport and camera through rename/reorder by stable member UUID. Pinned Properties retains its own target.

Lists use `offset` and `limit` (1–200, default 100) where provided; `nextOffset` identifies another page. Original bytes are bounded to 4096 bytes per request. RPC request lines are capped at 2 MiB, tool arguments at 1 MiB and JSON tool results at 4 MiB; large inspections should use paged properties/records/source bytes or JSON export. For 3D captures, width/height are maximum dimensions (1–4096 per axis); the image preserves its aspect ratio and the live viewport is not resized. Texture/window captures retain native dimensions. Returned PixelWidth/PixelHeight identify the actual output size. For non-image/non-3D previews use `capture` with `target=window`.

`capture` with `target=preview` requires the current `preview` UUID from `state`; missing or replaced identities return `stale_preview`. Successful preview captures include that UUID and the asset identity alongside the image. Window and Properties captures remain independent of preview selection. Explicit camera poses are clamped to the upright ±89° pitch range before returning, so immediate movement is safe even after a vertical requested direction.

Disabling MCP or closing zStudio cancels pending indexing, opening, preview loading/seeking and save work as well as queued operations. Indexing remains unavailable for manual cancellation. Operation cancellation is separate from the loaded workspace and preview lifetimes: stopping access after a completed request does not invalidate the retained preview. If an asset/document selection is still current when only its MCP load is canceled, the GUI retries that selected preview using its workspace lifetime; the original operation remains canceled. Navigation, document closure and shutdown prevent recovery of obsolete selections. Saves retain their existing atomic commit boundaries; shutdown cannot undo an already committed file.

Canceling an animation world bind, seek or level refresh recovers the still-owned request under the editor lifetime, including cancellation after mesh replacement. Recovery requires cancellation of the originating MCP request; ordinary GUI cancellation never restarts work over new user intent. Transport and seek-based option changes report `context_changed` when a GUI seek supersedes them, and failed binding/preparation reports `preview_unavailable`. Queued LOD changes observe request cancellation and restore the retained selection if canceled before mutation. Pending picker values cannot alter another seek's player or map geometry. Newer GUI LOD/Map/Horizon changes supersede earlier requests; refreshes retain playback intent and respect an explicit Pause. Initial world binding reconciles options changed during mesh or audio preparation before publishing. Audio preparation retries also observe operation cancellation; the editor remains available for another retry. Malformed keyframe payloads remain read-only, but `property_fields` with the default segment 0 still exposes available scheduling/catalog fields and a read-only Keyframe diagnostic. Nonzero segment requests are rejected when the payload cannot be decoded.

Static model/Whole world LOD, horizon, texture-pack and Whole world difficulty refreshes prepare a replacement before publishing it. Cancellation or load failure retains the displayed scene, camera, selection and preview UUID, and restores the option controls and shared saved difficulty to their published values. A successful replacement receives a new preview UUID; read `state` again before subsequent preview commands. This behavior is shared by GUI and MCP option changes. A newer GUI refresh superseding an MCP refresh makes that operation fail with `context_changed`, rather than reporting completion with an unpublished or obsolete preview ID. Failed preparation reports `preview_unavailable`. Reapplying an already-published difficulty remains a successful no-op after cancellation. MechWarrior 3 previews select authored missions instead: `scene_options`/`animation_options` difficulty requests return `unsupported` before changing controls or the shared RECOIL preference. While the shown preview has a scene-card draft, resource/content edits, undo, save and close for other documents return `pending_drafts`, because accepting them would refresh that preview; resolve the draft first.

Whole world adds `scene_options.changes.highlight`: `none`, `nonDefaultSoils` (yellow), `canModify` (green), or `clipTo` (red). The modes are exclusive and use solid RGB with original alpha/cutouts; only matching material surfaces/node instances change. `preview_state.highlight` returns that value for Whole world and `null` in other viewers. Requests for this option outside Whole world return `unsupported` before applying other changes in the same request. Highlight-only changes retain the preview UUID, camera, geometry, selection and document revision; existing preview/draft guards and asynchronous operation handles still apply. The latest GUI/MCP choice survives scene refreshes and navigation within the current application session. See [surface highlights](world-highlights.md).

`scene_options` validates every supplied option, including the active LOD range and available texture packs, before changing controls or preferences. In a batch with scene refreshes, the requested highlight is applied only after those refreshes succeed. Failed, canceled or superseded refreshes retain the prior highlight; a newer GUI highlight is preserved and reported as `context_changed` instead of being overwritten by a deferred request. Other successfully applied options follow their existing refresh-lifetime rules; a batch is not a transaction across multiple published scenes. Textured vertex-colored surfaces multiply decoded texture RGBA by authored vertex tint without preview lighting; untextured shaded mode retains view-dependent shading. GUI views and MCP captures share this renderer.

List `query` filters apply case-insensitively before pagination; totals refer to matching records. Reference indices, sequence/event UUIDs, pickup source identities and dispatch occurrences remain unchanged by filtering. Runtime pages also return `offset` and `nextOffset`. Search uses names/paths or displayed text appropriate to each list (event operands and diagnostic text are searchable). `ai_nodes` with `section: "constraints"` searches network member/name, constraint kind, and `edge_NN`, `attribute_NN` and `node_NN` endpoint labels (indices use at least two digits). Constraint search uses network member/name prefixes of 70 characters and a kind prefix of 256 characters. KindCharacters/KindTruncated report the original length and shortening. Parameters remains structured JSON but is limited to 64 nodes, depth 8, 2048 total text characters (including keys) and 512 per string; ParametersTruncated discloses omitted content, including prior reader truncation. Full resource data remains available through export. Filtering combines with the optional network ID; totals and page offsets cover only matching attributes, preserving each original edge/attribute identity. `preview_state` reports the active viewer's LOD/horizon and uses null for unavailable 3D controls in texture, sound or text views. A `workspace_view` request with an unavailable tab fails before applying any presentation changes. Structural edits with an unavailable sequence/event return `stale_record`; refresh `animation_records` before retrying.

Tools expose **capabilities that actually exist in this version**, including shared texture PNG import and prepared-script editing. Arbitrary binary patching and editing of read-only format families remain unavailable. Game callbacks and other engine-dependent preview approximations retain their existing support diagnostics. Exports use edited model/resource/texture/script snapshots where those editors are available; animation Save As and edited animation property inspection remain separate operations.

## Example editing workflow

1. `open_root` with the root path; await its operation. `open_document` with the full animation archive path; await it.
2. Read `assets`, retaining the returned document UUID and animation entry index. `select_asset` with those identities and `kind="Animation"` loads the shared preview.
3. Read `animation_records` for sequence/event UUIDs. Read `property_fields` for that exact target (and `segment` for keyframes).
4. Call `property_edit` with the document UUID, current revision, target, returned field ID and invariant text value. Compound fields use the delimiter shown in their current value. Read state again before the next accepted edit.
5. Preview with `animation_transport`; inspect diagnostics and `capture` output. Save through `save_document` with an explicit new destination, then await and inspect its operation result.

## Development contract

`zStudio.Application` owns the UI-independent command/schema contract. `zStudio.Mcp` adapts it to the official C# MCP SDK and a same-user named pipe; network logons are denied. `zStudio.Desktop` marshals command execution to the WPF dispatcher and coordinates mutations, async jobs and existing services. No port is opened and no game assets or external decompilation references are exposed as server configuration.

Every future user-facing feature requires MCP parity, typed schemas, documentation and meaningful tests in the same change. Discovery metadata is generated directly from the Desktop command registry into `src/zStudio.Mcp/CommandCatalog.json` and embedded in the connector; it contains no workspace data or duplicate editing implementation. After changing commands, regenerate with `dotnet run --project tools/zStudio.PreviewCheck -c Release -- --mcp-catalog src/zStudio.Mcp/CommandCatalog.json`. The parity test compares the entire generated catalog (names, descriptions, annotations and nested typed parameters) with the live registry; stale metadata fails CI. `docs/mcp-capabilities.json` is the independently maintained GUI action inventory. Tests compare actual XAML event handlers with it and verify that mapped tools exist. This is a review guard, not proof of behavior: bound controls, dynamically built forms and renderer interactions also require review and protocol tests. FieldEditor-generated properties and actions inherit exposure; binary validation remains shared. See CONTRIBUTING and AGENTS.

The SDK is pinned to [ModelContextProtocol.Core 2.2.0](https://github.com/modelcontextprotocol/csharp-sdk/releases/tag/v2.2.0). Visible startup uses the desktop-hosted shell automation object so clients which terminate their connector process tree cannot kill the user's shared workspace; the approach follows [Microsoft's desktop-shell guidance](https://devblogs.microsoft.com/oldnewthing/20131118-00/?p=2643).

## Archive and typed-resource editing

ZAR member CRUD and standalone/embedded ZRD structural editing have full shared GUI/MCP paths. The six resource tools, identity rules, draft behavior, save destinations, ownership conflicts and value formats are documented in [resource-editing.md](resource-editing.md). The generated catalog exposes 102 tools. Resource saves verify both bytes and shared-reader parsing before atomic replacement; new Save As destinations become the subsequent save target. Original-source inspection stays separate from edited payloads.

Standalone ZRD editing requires a complete bounded decode; malformed documents retain raw inspection with diagnostics and reject resource/save operations. Asset listings reflect current model replacements and appended records. Their `Offset`/`Length` describe the edited snapshot; nullable `sourceOffset`/`sourceLength` identify the original range for `source_bytes`. Pinned model Properties follows the same kind/index through replacement and undo/redo, and `properties_state` includes generated resource fields when a resource is pinned.


## Texture and prepared-script editing

The seven texture/script tools, direct PNG replacement and explicit variant batches, virtualized instruction editor, token limits, pinned drafts, shared ownership, snapshot previews and verified saves are documented in [texture-script-editing.md](texture-script-editing.md). `save_document` accepts a single new `destination` or a complete batch `destinations` map, and returns per-file successes/errors. A partial content Save As retains every requested destination; ordinary Save retries unpublished copies as new files, and pending copies keep the document dirty. Current Save As aliases cannot be added as separate texture variants. Working saves retain external-change and protected-source checks. `script_records` uses lifetime-stable entry/instruction UUIDs, not names or mutable row indices. Generated Properties includes asynchronous argument actions through `script_properties`.

AI network visualization has shared Whole world controls and three discovery/inspection tools. See [ai-networks.md](ai-networks.md) for scene options, graph identities, pagination, selection, framing and snapshot behavior.

AI node/network name queries use 70-character prefixes and skip search formatting for empty queries. Node name/type results cap 256 characters with original counts/truncation flags. MW3 node links use a shared 32-slot preview for rendering/cards/Properties/MCP, with `link_count`/`links_truncated`; network/preview state returns `linkSlots`/`linksTruncated` alongside the resolved preview link count. Complete links remain accessible through paged `zrd_nodes` and export. Motion state caps diagnostic and assembly previews with counts/truncation; `motion_preview action: "assemblies"` pages complete binding choices. Motion edits retain the separate closing sample exactly.

Motion assembly operations use a cancellable node-name index off the UI thread; `preview_state` remains available during binding, and superseded bindings cannot publish. Version-39 transform keyframe inspection validates the stored count against the complete payload. Invalid counts yield the shared read-only Keyframe diagnostic and reject segment access/actions, while scheduling edits retain malformed source bytes. These corrections use the existing operation, property and preview commands.

After `motion_preview action: "assembly"` selects an edited library member, the shared viewer retains its snapshot member UUID. Archive rename/reorder, model replacement and Undo/Redo keep duplicated/imported members bound even without a `SourceIndex`; `preview_state.motion.assembly` reports the resulting current index. Canceled selection leaves the previous binding identity intact. Deletion clears the binding, and reusing its index/name cannot select another member implicitly. GUI assembly selection uses the same path.

Identity lookup includes retained edit-history snapshots when a library load is overtaken by an edit or Undo/Redo; matching requires the exact decoded document instance, never equivalent names/bytes from a separate parse.

AI discovery, node selection/Properties and scene inspection also expose authored attack-strategy text, validity, normalized key and the shared node/arrow color. Missing strategies use red (#FF6666) nodes and connections; empty/invalid/unknown values remain gray (#A0A0A0), with their distinct metadata preserved. The selected AI marker's card displays its read-only Attack strategy field among the scrolling details below This AI network node, immediately above Status. `scene_card` field copy and Copy all return that same value once. `scene_inspect` keeps structured metadata outside the readable card fields as `attackStrategy` / `hoverAttackStrategy`; existing tools and input schemas remain compatible. See the AI guide for the bounded result shape and fixed palette.

## Source projects

Build profiles choose the mission texture packs: `source_status` lists them (built-in `original` and `modern`, plus `gamegen/build-profiles/*.json`, the default marked, and `selected`: the profile chosen in Tools → Build profile; a file that cannot be used is listed with its `error` and no packs, and only it is refused (when it is the chosen profile, `source_status` without `profile` still answers, with its `profileError` and no outputs); each pack gives its `file`, `automatic`, `budgetMiB`, `maximumDimension` and `missions`, null when every mission gets it; the automatic pack `rtexture*.zbd` becomes `rtexture<N>.zbd` per mission, and `budgetMiB` is the largest it makes) and its outputs follow `profile`, with each mission's automatic pack under its actual name (default: the chosen profile, else the project's default); `source_export` takes `profile` (with the same default) and reports it, with `notes` about packs left in the destination that the profile does not build and the game may load instead (or a destination folder that could not be listed). Its result also lists `lookups` (at most 256, with `lookupCount` and `lookupsTruncated`): the lookups by name the built missions make as the game loads them whose name several nodes share (`kind` texture effect, animation root, animation attachment (an animation's attach node outside its root, whose subtree its names are searched in first), animation name (a node or tracked-node name neither subtree nor the animation's own lights and sounds have) or animation prerequisite (the first node of an activation prerequisite's path), `name`, `source`, `candidates`, and the `found` node's path and `slot`; entries that share a name are listed separately). `lookupChanges` (at most 64, with `lookupChangeCount`) holds those that find another node than in the destination's files the export replaced, `before`, `after` and `uncertain` (true when the worlds were too large for the comparison to tell every copy apart, so the lookup may still find the same node), pairing a built world with the animations the destination keeps and built animations with its world, as the game would; they are in `notes` too. The texture-effect lookups are read from the load script and the scripts it sources as deep as a build follows them (32 levels, 1,000,000 instructions); a mission whose lookups cannot all be read (deeper sources, a script a macro names or one outside `gamegen`) is left out of `lookups` and `lookupChanges`, and `notes` (for a source world, its world output's warnings) say its lookups were not checked. An edit of a source world that makes a lookup find another node than when the world was opened or last saved is reported in `problems` until it is saved or taken back, and counted in the rebuilt document's `sourceWorld.lookupChangeCount`; a world that showed an older build when the project was saved (another world's edit changed a file it reads) is compared again from its first build that reads only saved files.

`source_reconstruct` rebuilds a Recoil source tree (`data/`, `gamegen/`, no zStudio metadata) from a shipped data folder into a new or empty folder and can open it as the workspace root. It reads the files in that folder and its mission folders (`mN`), as the game does; files elsewhere, such as a demo copied into a subfolder, are listed as not reconstructed and are not read. Only the original shipped files can be unpacked; any other folder, such as an export, fails with `invalid_argument` and "zStudio can unpack only the original ZBD files." A folder whose files would keep more than 1.5 GiB in memory together until every file is read (the releases need about 500 MiB) fails with `io_failed`, after removing what was written, and so does a game file that changed after the folder was listed and checked (another size or modification time, or other content in an archive the original-files check read). A root with `data` and `gamegen` folders is a source project; `open_root` with `project: true` opens only such a folder and refuses any other with `not_project`, as the welcome screen's source project **Open** does; a project that is a link (a junction or symbolic link) or lies below one is refused the same way, since its edits and saves would be written into the folder the link leads to. Opened as a plain folder, such a project can be browsed and exported, but its worlds, edits, saves and interrupted-save recovery are refused with `io_failed`. The welcome screen's **Initialize** dialog runs `source_reconstruct` with `open`; its Cancel cancels the operation, which removes what it wrote. Both paths must be full paths. Once the project is written, cancelling while it opens leaves it in its folder, unopened (so does the dialog's Cancel pressed after its last step, and the dialog says where the project is); a stopped reconstruction removes only what it wrote, keeping files another program put in the folder or changed meanwhile (a file another program creates at one of its paths stops the reconstruction and is never replaced); when what was written cannot be removed (another program holds a file), the refusal names the folder to delete. `source_status` pages the game files it can build with their source inputs; listing them walks `data` and `gamegen`, and a walk that would visit more than 250,000 files and folders (whatever they are) fails with `io_failed`, naming the folder. Cancelling the request stops the walk. `source_export` builds all outputs, or those listed in `outputs` (for example `["m1/zrdr.zbd"]`); without `destination` it only checks them, and with one it stages, re-parses and writes them (nothing is written if any output fails or a staged output changed after it was built, nor, failing with `invalid_argument`, when a project file it read, its build profile, its source list or a texture size that names an automatic pack changed before publication). Existing game files in the destination are replaced only with `overwrite`. Results list built/failed outputs (256 rows) with warnings (16 each) and bounded errors. Exported files work in the game but are not byte-identical to shipped files. Reconstruction and export are cancellable operations; an export canceled while publishing ends `canceled`, its message naming any file it could not undo (one another program wrote, or an original no longer in the backup folder). Text `.zrd` sources use the existing ZRD tools and save as text; `.gs`/`.gw` scripts open as read-only token text. Formats, layout and limits are in [source-project.md](source-project.md).

`source_world_open` shows a mission's world as its build script (`gamegen/mN.gs`) assembles it from the project, including the project's unsaved edits: zStudio builds the mission privately into the project's `zstudio/cache/worlds` folder (removed when the world closes; Files does not list it) instead of a temporary folder outside the project, as the export would (world, animations, resources and the 16-bit Direct3D texture pack, `rtexture16`, whatever build profile the project's exports use), and opens the world in Whole world with its mission context. Build problems go to `problems` under the script's path. The build is one state of the project: when another program changes a project file the build already read, or adds, removes or renames a source after the build listed the project's folders, the world does not open (`external_change`, naming the file) and nothing of the build is kept; open it again.

Every open world of a project edits one workspace. `undo_redo` on any of its worlds undoes the project's newest change, and `save_document` writes every changed source file of the project as one recoverable publication. That publication uses a journal and staging folder in the project's `zstudio` folder. A file another program changed since it was read is a conflict (`external_change`), and nothing is written. Each edit, `undo_redo` and `reload_document` rebuilds the world and returns the replacement document, whose ID differs:
- an edit the world cannot be built with is taken back and reported as `build_failed`;
- an edit whose rebuild sees another program change a project file, as above, is taken back and reported as `external_change`;
- an edit canceled before the rebuilt world is shown (`zstudio_operation` cancel, request cancellation or disconnection) is taken back too;
- a taken-back edit leaves the shown world, the workspace with its undo and redo steps, and `problems` as they were; the GUI status says it was reverted and why;
- while any world of the project rebuilds (`sourceWorld.rebuilding`), the project's other edits, `undo_redo`, `save_document` and `reload_document` return `busy`;
- while `save_document` (or the GUI's Save) writes the project's files (`sourceWorld.workspace.saving`), off the UI thread, the window and Properties are disabled and the project accepts no edit, undo, redo or reload: other MCP changes wait for an MCP save's operation, or return `busy` during a GUI save. `zstudio_operation`, `state` and other reads stay available. Cancelling stops the save only before it replaces a file (nothing is saved); from then on it finishes or is undone, and closing zStudio waits for it.

The replacement document's `sourceWorld.editNotes` (at most 16, 512 characters each, with `editNoteCount`) holds the edit's notes on its reach (a copy's part names, the copies of a part the edit reaches), which the GUI status shows after the rebuild, and `sourceWorld.lookupChangeCount` counts the lookups by name that find another node than when the world was opened or last saved (each a warning in `problems`; the status counts them too).

`close_document` of one of several open worlds keeps the project's edits; the last one needs `discard`, and returns `busy` while another world of the project is opening or rebuilding; a world that is rebuilding after an edit is never closed (`busy`), since that would take the edit back. Unsaved edits are dropped only by that explicit discard (or the GUI's Discard); otherwise they stay for the project's next world. Applying a source world's Properties draft with `resolve_drafts` rebuilds the world and returns the document that shows it now. `source_changes` lists the files `save_document` would write and the history, and for one `file` returns a bounded line diff of its working text against the disk. Document state's `sourceWorld.workspace` reports the same: revision, undo/redo labels, dirty files and history.

Editing commands:
- `source_world_models` pages the project's loadable glTF models.
- `source_world_add_model` loads one into the world:
  - `SetModelDirectory` for its folder and `LoadGameGen` go before the script line that writes the world.
  - A placed model (`position`, optional `heading` in degrees) is followed by `Object3DTranslate`/`Object3DRotate`, `FindNode %worldName%` and `AddChild`. `AddChild name` finds the newest node with that name, so a placed model that has a node of its own with that name is refused with `build_failed`.
  - Without `position` the model is an unplaced root, which resources such as `aiv.zrd` place copies of by name.
  - `source_world_definitions` lists definition files other missions list with an animation for the node name: the first 64 in path order, with `fileCount` and `truncated` (the GUI's Add model dialog lists the same files, and starts a truncated list unchecked). `definitionFiles` (default: all of them, refused above 64) appends them to the mission's `anim.zad`, keeping its comments and layout. An addition that makes another mission file fail, or makes the game reject one (an animation bound to a node, attachment or effect this world lacks), returns `build_failed` and is taken back; a stale world returns `stale_document`.
- `pickup_lock`, `pickup_move` and `scene_card` work in source worlds. A confirmed move of a pickup, AI vehicle or AI node changes only the coordinate tokens of the text resources the world's archives were built from, together with uniquely linked difficulty counterparts.
- `source_world_object` describes a node (`node` from `scene_nodes`):
  - its local transform (rotation in degrees about Y, then X, then Z) and flags: as the script's Object3DTranslate, Object3DRotate and Object3DScale store it when the build composed it from them, otherwise decomposed from the matrix (a mirror as a negative X scale);
  - its origin: the glTF file and node it was imported from, or the instruction that created it; `database` marks a node of the mission database or one of its parts, and `part` a node of a part (a file the database references, copied wherever it does, so an edit applies to every copy);
  - the instruction that last set each property, with how often it ran;
  - the property commands that fit it, and `editableFlags`, the flags its source can set (a script object has no command for `0x20000` no craters).
- `source_world_object_edit` moves, rotates or scales a node, or sets or clears one flag (`0x8` standable, `0x10` collision, `0x20` bounding-box collision, `0x40` proximity, `0x80` landmark, `0x10000` craters allowed, `0x20000` no craters). The change goes to the glTF node's transform or extras (for a model file, wherever it is loaded) or to the instruction that set the value. It is refused when that instruction runs more than once, takes the value from a macro, or no longer reads as it did when the world was built (reload the world); when it sits in a script another mission's world script also runs, the value is set in this mission's world script instead (below). A glTF node renamed since the build is refused the same way. A move changes only the position, keeping an authored rotation, scale or mirroring; a script value changes only the components that differ, so a macro in another component stays. For a glTF node with its own transform, a script `Object3DTranslate` still sets the position (so a move edits it), while script rotation and scale are ignored (so those edits change the glTF); an edit that would leave the glTF transform at identity while a script rotates or scales the node is refused, and so is a transform edit while a script sets the transform of another copy of a part's node or another load of a model file's node, also where another mission loads the file (that mission's scripts are followed as its build runs them, finding the node by name: a `FindSubNode` below a load of the file, or a `FindNode` of the name once the file is loaded, which the refusal says may find another node). A flag edit notes another copy or load whose script sets that flag (it keeps its value). A value nothing set yet is added after the instruction that created the node. When another mission's world script also runs the script that set the value (a shared `world.gw`, `weapons.gw`'s template flags) or, for a value nothing set yet, that created the node, the value is set before this mission's world is written instead, after a `FindNode` of the node, whose name must be unique: flag, transform and property commands set their values outright, so the last one gives this mission the value and the other missions keep theirs. Which other missions run a script is read from every source line their world scripts reach (whatever condition guards it), each script once; more than 50,000 scripts or 1,000,000 source lines in all, or a source line naming its script with a macro that another mission reaches, refuse the edit (`invalid_argument`) rather than take the script as this mission's alone. At exactly ±90° pitch the rotation shows yaw 0.
- `source_world_object_edit` with `action` `duplicate` (`name`, optional transform), `delete` or `parent` (`parent`: a node index, −1 for the world; a node of a part of the mission database becomes a root of the part) copies, deletes or re-parents the whole object the node belongs to (`object` in `source_world_object` names it): in the database's glTF, or through the script's lines (copies are loaded again before the world is written, deletions become comments). Deleting a database object is refused while a script instruction acts on it or one of its parts; deleting a script object turns the instructions on it and on the parts its load made into comments (a `FindSubNode` only when nothing else was ever attached below it) and is refused for other instructions, for objects attached below it that instructions act on, for a node with several parents, and for an object made by a script another mission also runs (no line of one mission deletes it exactly: a `DeleteTree` before the world is written would leave its nodes' slots in the world's node table). Copying a database object is refused while a script finds one of its parts by name. For a part of the mission database, which every copy of the part shares, instructions acting on any copy count, and a move is refused while a script sets the transform of another copy. A node its file places under several parents (an instance), or anything inside it, changes in every copy of the instance (transform, flags, copy, delete; refused when the copies differ); it does not move out of the instance, and nothing moves into one (also when a script took its other holders out of the world). A shared node without a zone of its own takes the zone of the copy the build reads first: a move or deletion that makes the build read another copy writes the zone it had onto every copy (refused when that zone came from references to a part in different zones), and a copy of a node holding one keeps that zone. Only sharing within the moved node's file counts: a part referenced from inside an instance is one copy in its file, so its nodes move within it. Moving a node already under the world is refused as no change, and a move keeps the node's zone (refused for a part's node whose copies take different zones from their references, where a zone of the file would replace them). A part's node is not copied while a script acts on one of its copies, and no node is copied while a script takes a part out of it (gamegen's morfUtil.gw does with morph LODs) or acts on a part its file holds elsewhere. A level-of-detail node moves only under a parent standing where its parent does in its file (relative to their size; a part's top is where its references put it), and a node a script left with no parent moves only in the scripts. A move is refused when a script's `NodeSetLighting` along either chain would light the object differently, and notes a level-of-detail node it moves under or out of; a group of the mission database moved where the build deletes it (to the top, or into such groups) must have no geometry and no transform. A script object moves through the scripts that made and attached it (each refused when another mission also runs it). A database object a script attaches elsewhere is not copied (the copy would stand where the file puts it), nor a script-loaded object whose parts scripts change; nothing moves under a node a script took out of the world. Copies check only the transform values that differ from the object's. The build finds nodes by name, so a copy or move in a glTF file can change which node a script instruction acts on: after the rebuild every instruction must act on the same nodes as before, including nodes the build frees again (the mission database's groups and root), or the change is taken back (`invalid_argument`, naming the first three such instructions with the nodes before and after, and how many more). A node its file places under several parents is the same node whichever of its copies the build reads, and a node inside one is known by its name among its siblings, so a copy made beside one leaves the others the same nodes. A script object does not move where it would need a sheared transform (under or out of a turned parent whose scale is not uniform), and a node whose transform holds a shear or a zero scale keeps its rotation and scale (it can still move, or be copied in place or with a new position); a scale of 0 (or below 0.00001) is refused, since it leaves no rotation to read back, and a move that would flatten a node or place it beyond ±1,000,000 of its new parent is refused. Copy names cannot end like an editor's `.001` suffix. Omitted duplicate transform values come from the whole object; with only `position`, a database copy keeps the original's exact rotation, scale and mirroring. A database copy without a transform sits where the original was built and keeps the flags scripts gave it; other instructions that find the original by name are listed in the notes. Re-parenting a database node is refused while a script sets the transform of the node or of a node along either parent chain. The duplicate result includes the copy's node index (`copy`; for a part the database copies several times, the copy made beside the node copied) and every copy's (`copies`, at most 256). Edits planned from a world whose build read a source changed since (another world's edit, an undo) return `stale_document` until `reload_document`.
- `source_world_command` sets a property command, for example `WorldSetFogColor`, `LightSetDiffuse` or `CameraSetFOV`, in the same way.
- `source_blender_checkout` (a `model` path, or `document` and `node`; an operation, which can be cancelled) copies a model with its buffer and textures into `zstudio/export/<id>/input` for Blender; the copy marks transparent textures, hides the collision volume of a model a mission's build loads as a pickup as the game draws it (the file the load finds through the model folders its scripts set, not another file of that name), and states every node's zone (or marks it `zoneFromLoad`; the copies of a shared node state the zone of its first copy, which the build reads) so that nodes Blender moves keep their zones (the project's file is unchanged). It is refused with `busy` while a world of the project rebuilds, and with `context_changed` when the project changes while it copies, by an edit in zStudio or a file another program changes (the partial copy is removed, as after a failure or cancellation); a model the build could not read, or one using more than 4,096 buffers, 4,096 textures or 512 MiB in all, is refused with `invalid_argument` before anything is copied. `source_blender_checkouts` lists checkouts and the exports found in their outboxes, off the UI thread and cancellable (as Tools > Update from Blender export does); a `zstudio/export` folder holding more than 250,000 files and folders in all (the files the checkouts' manifests list included) is refused with `io_failed` rather than listed in part. `source_blender_update` applies an export: it seals it, reads it as a build would, and makes it one change of the model's glTF and buffer and every new or changed texture, returning notes about shared textures, missing node names and scripts (this mission's or another's) whose rotation or scale of a node starts or stops applying because the export gives the node a transform of its own or removes it, and the changed `files` (at most 256, with `fileCount`; notes at most 32, with `noteCount`). The update leaves out again the zones the checkout stated where the file's hierarchy gives them, and gives a moved mission database group's transform to its objects; it is refused (`invalid_argument`, saying why) when the copies of a shared node (`instance`) differ, when a node marked `zoneFromLoad` moved under a node with a zone in the file, and for a group with geometry or a moved group whose objects are in a part's file or that holds a level-of-detail node or a shared node. `source_blender_checkouts` lists at most 32 checkouts (`checkoutCount`) with at most 16 exports each (`exportCount`); `source_recovery_resolve` lists at most 64 changed files and conflicts (`changedCount`, `conflictCount`). Embedded textures are refused. Buffers of one name from different folders get numbered checkout copies; a model that uses two different textures of one file name (the engine finds textures by name) is refused by the checkout, and an export with two different PNGs of one name by the update. When the model or a texture changed in the project since the checkout, or the export would replace a project texture the checkout did not include, the update returns `conflict` naming the files; an export without the model's engine attributes (Custom Properties off) also returns `conflict`. `force: true` applies the export anyway.
- Terrain: `source_terrain` lists the project's recipes with the pieces each compiled to in the world, or one recipe's surfaces, defaults and regions (with `region`, its shape's coordinates up to 4,096 points at whole polygons, with `truncated`, `pointCount` and `squareUnits`). `source_terrain_edit` changes a recipe as one undoable change: `set_defaults`, `add_region`, `update_region`, `remove_region`, `move_region`, and `paint` with `mode` paint or erase and a stroke (`path` of [x, z] points with `radius`, or `polygons`). Attribute patches set keys with values and remove overrides with null. `source_terrain_create` creates a recipe for meshes of a glTF file and its marker in the mission database (refused for the database itself and for a file it references, such as one of its parts, whose nodes stay objects). `source_terrain_convert` plans (and with `apply` performs) Convert to editable terrain: surfaces, converted pieces and the objects kept with reasons, then a `probe` comparison of the converted area before and after, searching each point's grid cell and the world's own list as the engine does (`samples`, `spacing` (wider than requested over an area that would exceed 4,000,000 samples), `hits`, `mismatches`, `heightOnly`, `revealed`: points where the converted terrain finds ground the original pieces hid from a neighbouring cell, `examples`). Cancelling the operation during the comparison leaves the conversion applied: the operation completes with the new document and `probe: null`. The plan is made off the UI thread and cancelling stops it; it returns `busy` while an export, validation or other source operation runs, `stale_document` when the world is rebuilt or closed meanwhile and `context_changed` when the project's sources change meanwhile. Sources naming more than 262,144 different words (or wildcard patterns of more than 256 Ki characters) are refused with `invalid_argument`. `paint` refuses a region that covers its whole surfaces; `update_region` with `wholeSurfaces: false` makes it cover nothing first. Terrain pieces are build output, so `source_world_object_edit` refuses them.
- `source_recovery` lists interrupted saves with the state of each file (read off the UI thread; the request's cancellation stops it, also while it lists `zstudio/recovery`, where more than 250,000 files and folders fail with `io_failed`). `source_recovery_resolve` (an operation, which can be cancelled) rolls one back, completes it or abandons it; files changed by another program are never overwritten. It reads, hashes and moves the files off the UI thread while the workspace is disabled as during a save (other mutations return `busy`; Tools → Resolve interrupted save resolves the same way); both commands hash a file only when its size is one the save recorded, so a file another program replaced with something larger is reported as changed without being read. Cancellation, a change of root or closing zStudio stop it between two files (or while it reads files to check them: a completion checks every file before it changes any, a rollback the file it reaches), never during one: the journal records what it did, the save still needs a decision (any action resolves it from there), and an operation canceled after it changed files says which in its message (also listed in Problems); one completed with its result stays completed. While an uncommitted one exists, saving is refused.

Source recovery responses list at most 32 saves with 64 files each. Resolution responses list at most 64 changed paths and conflicts. Each path keeps 256 characters plus an ellipsis when shortened; `fileTruncated` identifies shortened file fields and `pathsTruncated` identifies shortening in the changed-path list. The existing counts report full collection sizes. Before constructing these responses, recovery limits all manifests and event logs together to 64 MiB and 50,000 file rows; exceeding either returns an actionable error.

Large paths shorten `source_world_models` pages without shortening the paths used to select a model; follow `nextOffset`. `source_blender_checkouts` accepts `offset` and returns `nextOffset`: up to 32 checkouts per page, with a shared response budget that can shorten a page or its nested file/export lists while keeping returned paths whole. Counts still describe the full collections. Reading checkout manifests shares a 64 MiB budget before JSON parsing. Workspace/history path summaries in `source_changes` and document state keep 256 characters and report `pathsTruncated`; underlying source identities remain complete.

## Comparing worlds

`world_compare` (an operation, like Tools → Compare worlds…) compares two GameZ worlds given by full path, `retail` (expected) and `rebuilt` (actual), in the visible Compare worlds window; it needs no open folder. Either may be a version-13 world of the 1998 demos; the result gives both versions (`retailVersion`, `rebuiltVersion`). Files above 256 MB are refused, and a file that is not a GameZ world fails with `invalid_data`. The two node trees are merged by parent-child structure, independent of node order and slots: children match by name, repeated names first by their whole contents (rotation included), then by their structure, their children's names and their nearest position, however many copies share the name. Each list of copies is paired once however many places share it; a name with more than 2,097,152 candidate pairs, and every name once the comparison has examined 16,777,216 pairs of positions, pairs its remaining copies in order instead, and `approximatePairing` says so (their differences, and the whole-world lookups that depend on them, may come from the pairing). The result counts the merged rows that are the same, changed (class, flags, zone, grid cell, transform, class data, model or number of children), only in the retail world or only in the rebuilt one, and all the `differences` found. Class data is compared without the stored pointers, slots and runtime counters it holds, and the nodes it names (a camera's world, window and horizons, a light's worlds, a world's lights and sounds) by name; a model by every value it keeps: display mode and flags, texture scrolling (`model.scroll`), morph factor (`model.morphFactor`), its point entries (lens flares) without their runtime fields (`model.points`), bounds, and its polygons (`model.polygons`), whose corners carry their positions, UVs, normals and morph deltas and whose materials all their fields. A node under several parents appears under each, so the tree stops growing at 500,000 rows or 256 levels: `truncated` says so, and the rows whose children it leaves out say so too (their pairs are still matched for the name lookups below, unless `pairingTruncated`). It also gives the names several nodes share and how many of them a whole-world lookup (the engine finds a name's highest slot first) resolves to another node in the rebuilt world. Animations bind their roots and fall back to such lookups, but search their own subtrees first, so not every one changes behaviour. An indistinguishable copy (the same parents and the same contents all the way down, as the comparison sees them, so not their stored pointers) counts as the same node; the comparison makes at most 1,048,576 such copy checks in all, and `wholeWorldLookupsUnchecked` counts the differing lookups it could no longer check, which may find the same thing. A newer comparison replaces the window's rows; the previous `context` becomes stale.

`world_compare_tree` reads the merged tree: without `row`, its roots (the world node with its members, then the nodes no parent holds); with `row`, that row's children. `differencesOnly` keeps rows that differ or hold differences below them, and `query` keeps rows whose name, or a name below them, contains it; both filter MCP reads only and leave the window's own Differences only checkbox and filter, reported as `windowFilter`, unchanged. Each row gives both slots and classes, its status, how many rows below differ, `wholeWorldLookupDiffers`, `truncated` (the tree leaves out some of its children), `differenceCount` and at most 16 of its differences, with fields shortened to 64 characters, values to 256, and fields and values to 1,024 in all, so that a full page stays well within the response limit whatever its text. A pair lists at most 64 differences and counts the rest, as the window does (its last property line, More differences); `selected` and `row` also give `properties`, the window's property lines for both worlds (slot, class, parents, children, flags, zone, grid cell, position, model, then the other differences), at most 32 of `propertyCount`. The tool only reads the comparison and stays available while operations run. `action` `expand`, `collapse` and `select` change only the window's presentation (select opens the row's ancestors and shows its properties side by side); they need the current `context` and return `busy` while a dialog is open.

## Authored MW3 AI valves

`zstudio_ai_valves` accepts `document`, `member`, `section` (`records`, `references`, `targets`) and ordinary paging/query arguments. Returned record and operand UUIDs belong to the current edited resource. Names are not identities.

Record queries compare the complete authored name and numeric node/edge references separately before paging; they do not concatenate large source strings. Returned names remain bounded and disclose `nameCharacters`. Shared Whole world coordinate editing indexes existing typed resources, retains at most 256 diagnostics plus an omitted-count summary, and rejects AI-node or MW3 actor positions outside ±1e12 before preview, history or save. GUI and MCP use the same checks.

`zstudio_ai_valve_edit` requires `document`, `revision`, `member` and `action`. Operations are `set`, `add_record`, `add_binding`, `delete`, `duplicate`, `move`, `add_action`, `add_term`, `delete_item`, `duplicate_item`, `move_item`, `add_option` and `remove_option`.
